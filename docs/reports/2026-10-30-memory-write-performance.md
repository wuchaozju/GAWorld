# 记录阶段记忆写入合批：第三阶段

日期：2026-10-30。目标：减少同一步记录的 SQLite 提交次数，保留原有认知和即时记忆回顾。

## 改动

`gaworld/sim/_stages.py` 的 `_stage_record` 过去为 log、plan、reflection、action 分别调用单条写入、分别提交。现在将四条连续记录交给 `gaworld/memory/store.py` 的小批量 API `vector_db_add_entries`，一次事务完成。在四条均非空的典型情形，提交次数从 **4 次/步降为 1 次/步**。

单条 `vector_db_add_entry` 的参数及返回语义保持兼容，委托同一实现；正常成功写入的文本净化、嵌入调用和顺序、字段、权重、时间戳生成方式不变。全部嵌入 payload 准备好后再打开写事务，避免持有数据库写锁等待网络嵌入。新增 `memory.write` 计时指标，计量单条或合批调用的准备及提交总耗时。

只合并 record 阶段没有认知读取间隔的四条记录。`episode` 写入后紧接记忆回顾，仍保留原即时提交。没有跨 tick 缓冲，没有调整模型调用、认知频率、居民顺序、日志/Recorder 刷新和轨迹格式，也没有修改用户运行配置或比较 epoch。

## 可见性与失败语义

- 成功返回时整批已提交，下一阶段、下一居民及其他数据库连接可以立即读取。
- 空文本继续跳过；空批次不创建数据库、不调用嵌入。
- 嵌入准备失败时不写入半批；SQL 失败时整批回滚并抛出原异常。原四次提交在失败前可能留下部分行，**此异常路径现在改为组内原子性**，不声称异常后的部分产物完全相同。
- 该 API 与原单条 API 一样会提交当前连接，不支持放在调用方自管的嵌套事务中。嵌入在事务外的保证以入口尚未开启事务为前提；实际 record 路径满足该条件。

## 本地基准

对照是 Git `51cd67580a1836a3c047db15529c274becc0f23c` 的原单条写入函数，经 AST 提取独立执行；没有用已经共享新实现的 wrapper 充当旧基线。

环境：Python 3.12.9、SQLite 3.45.3，临时数据库使用现有 WAL/NORMAL 配置。每轮 250 组、每组 4 条，共 1000 条记录，各模式重复 5 轮，交替测量新旧算法。固定墙钟用于验证时间戳字段，测量使用 perf_counter；没有模型或网络调用。提交计数在计时区间外通过 SQLite trace 单独验证。

| 场景 | 原实现中位 ms/1000 条 | 新实现中位 ms/1000 条 | 局部提速 |
|---|---:|---:|---:|
| 固定向量，隔离写入开销 | 75.852 | 42.061 | 1.80× |
| 现有哈希嵌入与写入完整路径 | 84.097 | 63.029 | 1.33× |

每轮完整数据库行（包括 ID、内容、元数据、向量、默认字段）及 Top K 检索结果逐项一致。新旧各有 1000 次嵌入调用，没有通过少写数据或少生成嵌入换取加速。原始各轮耗时、行哈希和断言结果保存在 `output/performance/2026-10-30-memory-write-benchmark.json`，属于本地生成产物。

这些是本机存储子系统数据，不代表真实模型整场模拟提速。磁盘、数据长度、嵌入提供方和检查点频率都会影响实际收益。哈希嵌入场景包含当前默认嵌入准备工作，固定向量场景主要用于观察写入与提交开销。
