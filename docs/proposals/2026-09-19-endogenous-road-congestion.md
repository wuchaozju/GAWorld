## 一、动机:补上 agent→环境的第二条通道

### 1.1 现状核查(全仓 grep,非推测)

| 事实 | 位置 |
|---|---|
| `set_edge_congestion` / `get_edge_congestion` / `clear_congestion` **零调用点** | `city_map.py:1627/1632/1636` |
| 因此 `_route_congestion` 恒返回 1.0,路上永远不堵 | `city_map.py:1157` |
| 唯一跑通的 agent→环境闭环是节点占用 | `world/local_physical.py:52` |
| 边上**没有** capacity 字段 | `_make_edge`,`city_map.py:598`(只有 source/target/road_type/bridge) |

**读侧已经全部接好**:`travel_plan`(`city_map.py:1256`)已经调用 `_route_congestion`、用它乘通勤时长、并把 `congestion` 写进返回的 plan(`city_map.py:1278-1281`)。
**本提案只补写侧。** 这是它成本极低的根本原因。

### 1.2 为什么先做这条

- 与节点占用**完全同构**:从 agent 状态重算 → 写回 `city_map` runtime → 下一 tick 被读回。没有新概念,没有新架构。
- Bench 收益直接:Track A 的两个锚点(杭州单程通勤 34.5min、公交机动化分担率 47.6%)现在是**循环论证**——参数写进模型再量出来。有了内生拥堵,通勤时长才是涌现量而不是读数。这是 `GAWORLD_BENCH_DESIGN.md` 里"Track A 近乎循环论证"那条批评的最短解。
- Track B 第一个**经环境中介**的 stylized fact:出行时刻的双峰(早晚高峰)。现有系统里任何涌现都只能来自社交图传染,拿不到这一类。

## 二、机制选型:BPR

`t = t0 × (1 + α·(v/c)^β)`,默认 `α=0.15`、`β=4`。

**为什么是它,不是自己编一个**:
- BPR(Bureau of Public Roads)link performance function 是交通分配领域的标准形式,α/β 有公开的标定区间。按机制来源分级它是 **(b) 文献标准机制**,不是 (c) 合理猜测——由它支撑的 Bench 结论可以单独立论。这一点在大五人格共线性闸门之后应该成为默认要求。
- `β=4` 的四次方形状意味着 `v/c < 0.8` 时几乎无影响、越过 1.0 后急剧恶化,正好是"平时不堵、高峰堵死"的定性形状,**不需要额外的分段/阈值逻辑**。

**否决的备选**:
- 线性拥堵:太平,做不出高峰断崖,等于给通勤时长加了个噪声。
- 排队模型 / 元胞自动机(NaSch 等):精度高,但需要 sub-minute 时间步,与本仓 10–30 分钟 tick 根本不兼容。

## 三、设计

### 3.1 数据流(与占用度同构,一 tick 滞后)

```
tick T    :各 agent 走 move 阶段 → on_agent_post_step 累计本 tick 的路段流量
tick T+1  :on_time_tick 把上一 tick 的流量折成 congestion 因子写回 city_map
            → 本 tick 的 travel_plan 读到它
```

**一 tick 滞后是刻意的,不是妥协。** 同 tick 内读写会让 agent 的遍历顺序决定谁堵谁不堵,直接破坏确定性——而 Bench 的 trust 项本来就还是 UNVERIFIED,不能再引入顺序依赖。占用度已经用 `node_occupancy_prev` 走过同一条路。

### 3.2 接入点(主循环零改动)

两个钩子已存在,且已经携带全部所需数据:

- **`on_agent_post_step`**(`generative_city_sim.py:4740`)携带 `step=step_ctx`,其中 `step_ctx["_travel"]` 由 `_stage_move`(`:3434`)写入,含 `route`(节点名列表)、`mode`、`status`。
- **`on_time_tick`**(`:4632`)携带 `agents` + `city_map`;`LocalPhysicalPlugin._refresh_map` 已经挂在这里。

新增 **独立的 `TrafficPlugin`**,不并进 `LocalPhysicalPlugin`——两者生命周期一致但可独立开关,合并会让一键回退退不干净。

### 3.3 流量口径

只有占用机动车道的出行才计流量。按 `_travel["mode"]` 分配 PCU(passenger car unit):

| mode | PCU | 说明 |
|---|---|---|
| car / taxi | 1.0 | 基准 |
| bus | 2.0 | 占路多(载客多是另一回事,见 §7) |
| e-bike / bike | 0.2 | 非机动车道,轻微干扰 |
| walk | 0.0 | 不进机动车流 |
| metro | 0.0 | 独立线网,不占路 |

**`status` 取 `arrived` / `departed` / `in_transit` 都计流量。** 这是本提案最容易踩错的一步:`move_agent`(`sim/_location.py:257`)只在 `travel_minutes > step_minutes` 时才置 `in_transit`;默认 10–30 分钟步长下,小镇内**绝大多数出行在一个 tick 内完成**,只数 `in_transit` 会漏掉几乎所有车次,拥堵永远为零。
一次跨多 tick 的出行,在它跨越的每个 tick 各计一次——它确实在路上占了那么久。

**路段归属**:`_travel["route"]` 是节点名列表,相邻两点即一条边,复用已有的 `_edge_key`(`city_map.py:1074`)。整条路线的每条边各 +PCU。

### 3.4 道路容量

边上没有 capacity 字段,按 `road_type` 给默认值,写法参照 `ROAD_TYPE_SPEED_FACTOR`(`city_map.py:94`):

| road_type | 容量(PCU/小时/方向) |
|---|---|
| arterial | 1800 |
| collector | 900 |
| local | 400 |
| road(兜底) | 900 |

按 tick 折算:`capacity_tick = capacity_hour × step_minutes / 60`。

### 3.5 抽样比 —— 本提案最大的建模风险

N=100 / 500 的仿真种群是真实小镇的**抽样**。直接拿 sim agent 的车次去比真实路段容量,`v/c ≈ 0`,拥堵永不发生,整个改造等于白做。

必须引入 **`agents_represent`**(每个 sim agent 代表多少真实出行者),流量放大后再比容量。

**它是建模旋钮,不是人口学事实** —— 与 `family.pairing.in_sim_pair_share` 同类,必须同样对待:
- 默认值从种群规模与目标城镇人口推出(500 人代表 5 万人 → 100),不硬编码;
- 进 Bench 的机制来源表,标 **(c) 类**;
- **任何依赖拥堵强度绝对值的结论都不得单独立论**,只能用跨取值的方向一致性立论。

### 3.6 与既有 rush hour 的双重计数 —— 必须先拍板

`travel_plan`(`city_map.py:1274-1281`)现在**先**乘 `RUSH_HOUR_TIME_MULT = 1.45`(`:64`),**再**乘 `_route_congestion`。而 `RUSH_HOUR_TIME_MULT` 本身就是"高峰期路上更慢"的**外生代理**——正是本提案要内生化的那个东西。两个一起开,同一个现象被算两遍。

| 选项 | 做法 | 评价 |
|---|---|---|
| **A(推荐)** | 内生拥堵开启时,时间侧 `RUSH_HOUR_TIME_MULT → 1.0`;价格侧 `RUSH_HOUR_TAXI_SURCHARGE` 保留(那是计价规则,不是拥堵) | 高峰慢改由"早高峰大家都在通勤 → 流量真的高"涌现出来。代价:关闭内生拥堵时必须自动恢复 1.45,否则一键回退退不干净——这是配置耦合,要写测试锁住 |
| B | 两者都留,`RUSH_HOUR_TIME_MULT` 调到 ~1.15 当残差项 | 折中,但说不清残差代表什么;调参无依据 |
| C | 什么都不改 | 系统性高估高峰通勤时长,直接污染 Track A 的 34.5min 锚点。等于让新机制去补一个已经被别处补过的洞 |

**这是本提案唯一需要决策的取舍。**

## 五、验证门

1. **零效应回归(硬门槛)**:`traffic.enabled=False` 时,逐 tick agent 状态与改动前**逐位相同**。所有外部性改造的共同地基。
2. **单元**:BPR 在 `v/c = 0 / 0.5 / 1.0 / 2.0` 的取值;PCU 归属正确;walk/metro 不产生流量;**一 tick 滞后成立**(打乱同 tick 内 agent 遍历顺序,`edge_congestion` 结果不变)。
3. **确定性**:同种子两次跑,`edge_congestion` 表逐 tick 完全一致。顺带把长期 UNVERIFIED 的 trust 项往前推一格。
4. **Track A 锚点(核心收益)**:开启后通勤时长分布均值向 34.5min 靠拢,且**不是靠调 `agents_represent` 硬凑**——判据是"跨 `agents_represent` 的若干取值,通勤时长单调上升,且在某个区间内与锚点相符"。**单点命中不算通过。**
5. **Track B(真正想要的)**:出行时刻分布涌现双峰,且高峰**锐度**随 `agents_represent` 单调上升。这是 GAWorld 第一个经环境中介的 stylized fact。
6. **跨种子**:所有判定至少 3 个种子聚合,判据用基线相对(`|处理组 − 参照组| ≤ 2 × 参照层跨种子标准差`),不用绝对常数。group agent 那两条教训——单种子判定就是噪声、判据要基线相对——原样适用。

## 六、风险

- **正反馈**:拥堵 → 改路线 → 新路线堵。BPR 的软饱和 + EMA 阻尼 + `max_congestion` 上限三重保护,但仍需发散检测(某条边连续 N tick 顶到上限 → 报警)。
- **小图效应**:程序化生成的小镇路网边少,所有人共用几条主干道,可能过度拥堵。缓解:先在 `python -m gaworld.population --size 500` 生成的镇上跑,看边流量分布是否过度集中。
- **与空间规避偏好(P4)的交互**:`redirect_for_aversion` 改变**地点**,拥堵改变**路线成本**,叠加后行为难归因。→ 见 §7:第一版**不**内生化路线选择。
- **成本**:零新增 LLM 调用,纯规则。每 tick 额外计算 `O(出行数 × 路线边数)`,可忽略。

## 七、不在本提案范围(刻意留出)

- **路线选择内生化**(拥堵感知的路径规划)。第一版 `shortest_path` 仍按距离排序,拥堵只影响**时长与成本**。理由:先让拥堵这个量本身被验证,再让它反过来改变生成它的行为——否则第一天就是一个闭合的正反馈,出了问题分不清是机制错还是标定错。
- **公交/地铁运力约束**(挤不上车)。属于 P3 场所容量那条线。bus 的 PCU=2.0 只表达"占路",不表达"载客"。
- **拥堵进入感知文本**("今天路上特别堵")。可以做,但要等数值先被校准——否则是在给一个还没标定的量写叙事。

## 九、标定结果（2026-09-19，实现后补）

工具：`benchmark/calibrate_traffic.py`（零 LLM；跑真实地图 + 真实家/工作地推断 + 真实方式选择 + 真实 `travel_plan`，只有**出发时刻是强加的**）。
样本：`gaworld.population --preset cn_county_town --size 500 --seed 7`，其中 331 人有通勤；地图 `data/citymap.md`。

### 9.1 机制本身是对的

| agents_represent | 通勤均值(min) | p90 | 峰值 v/c |
|---|---|---|---|
| 1 | 12.9 | 16.0 | 0.01 |
| 25 | 12.9 | 16.0 | 0.29 |
| 50 | 12.9 | 16.0 | 0.58 |
| 100 | 13.1 | 17.0 | 1.16 |
| 200 | 14.7 | 22.0 | 2.31 |

单调，BPR 的 β=4 形状清晰可见（v/c 越过约 0.6 才开始咬人）。这部分符合预期。

### 9.2 但 §5 的 Gate 4 不可能通过 —— 而且原因不在 P1

**自由流通勤均值只有 12.9 分钟，锚点是 34.5 分钟。** 拥堵只能让出行更慢、不能更快；要把 12.9 拉到 34.5 需要平均 2.7 倍的拥堵倍数，超过 `max_congestion` 上限，且意味着全城永久瘫痪。**这个缺口不是拥堵能补的。**

`--diagnose` 指出三个都**先于拥堵**的上游问题：

1. **地图空间尺度不足**：通勤距离均值 2.58 km，中位 2.83，p90 3.32，max 6.04。34.5 分钟的真实通勤对应大约 8–12 km，当前地图只有约三分之一。
2. **出行方式分布不真实**：e-bike 208 + bike 101 = 93%，metro 21，**bus 0，car/taxi 0**，机动化出行只占 6.3%。
   → **Track A 的另一个锚点「公交机动化分担率 47.6%」在当前地图上根本测不出来**，因为几乎没有机动化出行可言。这是 `choose_transport_mode` 的距离阈值（1.2 km 以内走或骑、3.2 km 以内 e-bike）遇上 2.58 km 中位距离的直接后果，不是模式选择写错了。
3. **家/工作地分配退化**：最大居住地占 21.8%（`_infer_home` 在中心 top-5 residential 里随机选），**最大工作地占 56.2%** —— 一半以上的人在同一栋楼上班。
   → 后果：**171 条边里只有 19 条被用到**（89% 的路网从无车辆经过），v/c 不低于 0.8 的边只有 1 条。所谓「拥堵」就是这一条路。

### 9.3 结论与取舍

- **P1 的实现不需要改**。它在当前输入下的行为正确，问题在输入。
- **不要按「命中 34.5 分钟」去标定 `agents_represent`**。那等于用一个旋钮补三个上游缺陷，正是 Bench 设计里批评的循环论证，而且会把拥堵标定成某一条路的属性。
- **§8 问题 2 的答案因此定为「强制显式设定」**：默认 `agents_represent=1.0`（拥堵层实际惰性），不自动从种群规模推导 —— 自动推导会把一个在退化分配上标出来的数固化成默认值。
- **按 v/c 标定而不是按时长标定**：真实城市早高峰主干道 v/c 常在 0.8–1.0。当前地图上 represent 取 75–100 能让最忙的那条边落进这个区间；但在负荷集中度修好之前，这个数只对那一条边有意义。
- **Gate 5（双峰涌现）仍未验证，且本工具不能验证它**：出发时刻是强加的，双峰是输入不是涌现。需要真实 run。

### 9.4 这照出了三个先于 P1 的待办

1. 地图空间尺度校准（通勤距离分布对真实口径）—— 决定 34.5 分钟锚点能否成立。
2. `_infer_workplace` 的目的地集中问题（按容量或距离加权采样，而不是取最近的匹配点）。
3. `choose_transport_mode` 的阈值在小尺度地图上把公交挤没了 —— 公交分担率锚点依赖这一条。

三条都是既有问题，只是被拥堵层照了出来。在它们修好之前，Track A 的两个通勤锚点都属于「量的是自己写进去的参数」。

复现：

```

python benchmark/calibrate_traffic.py --profiles <dir>/calib_profiles.md --diagnose
```

## 十、可观测性（2026-09-19，§8 问题 3 的答案：接）

标定那一轮的教训很直接：拥堵是个看不见的内部量时，调参只能靠一个一次性脚本。所以接了三层，**主循环仍然零改动**。

1. **单趟可见**：`move_agent` 之前把 `travel_plan` 算出的 `congestion` 丢掉了，现在带进 travel dict（在途/到达/出发/原地四种状态都带），并存进 `locations["travel_congestion"]`，使在途的那一步也能报出它是按什么倍数规划的。
2. **逐步落盘**：`TrafficPlugin` 每个 tick 往 recorder 的 `traffic.tick` 表写一行——**不管堵不堵都写**。一条恒等于 1.0 的平线不是噪声，它正是 §9 那个结论（种群抽样太小，路根本填不满）唯一能被后来人看见的形式。字段：有车路段数、拥堵路段数、总车流 PCU、最大/平均倍数、最堵的三条边。
3. **面板可见**：`external_systems_api.traffic_runtime()` 读 `output/records/traffic.tick.jsonl`，挂在「外部系统 → 外部环境」页签下的一张「道路拥堵」卡片上（不新开 tab——拥堵是环境量，而新 tab 要同步 11 处）。

卡片刻意区分三种状态，因为它们含义完全不同：

| 状态 | 含义 |
|---|---|
| 文件不存在 | 拥堵层没开，或这轮没写出来 |
| `ever_congested = false` | 层开着、车在跑，但**没有一条路堵过**——每趟都是自由流 |
| 有拥堵记录 | 正常，列出最近若干步与最堵的边 |

第二种是小种群下最常见、也最容易被误读成"模型很安静"的情况，卡片直接把它标红并指向 `benchmark/calibrate_traffic.py --diagnose`。

## 十一、上游修复之二：地铁可达性（2026-09-19）

§9.4 第 3 条。锚点「公交机动化分担率 47.6%」原本测出来恒等于 **100%**，根因不是阈值要调，是一个谓词问一个错问题。

### 11.1 根因

`choose_transport_mode` 判断能不能坐地铁的方式是**扫描驾车路线上有没有地铁站**：

```python
route = shortest_path(city_map, origin, target)
route_uses_metro = any(_slug(stop) in metro_stop_set for stop in route)
```

路过一个站，不等于这个站能把你送到目的地。实测：默认地图 130 个节点里只有 10 个地铁站，而 **95.5% 的通勤路线「经过」了其中一个**。于是：

- 3 km 以上、路线过站 → 一律 metro，**bus 分支永远轮不到**（它排在 metro 后面）；
- 6–10 km 的 `metro if route_uses_metro else car` → **car 永远是 0**；
- taxi 只在目的地名字含 Airport/Rail/Station 时出现 → 也是 0。

一个过宽的谓词同时废掉了公交、小汽车、出租三种方式。

### 11.2 修法

`metro_is_usable(city_map, origin, target, access_km=0.8)`：**两端各自都在同一条线的某个站点步行圈内，且不是同一个站**。顺带去掉了那次 Dijkstra——`route` 在这个函数里只为这一个判断而算。

另外把 >10 km 那条兜底从「非机场即 metro」改成「非机场则看可达性，不可达就是 car」，同一类错误。

`METRO_ACCESS_KM = 0.8` 写成模块常量而不是配置项：实测 0.5 / 0.8 / 1.2 km 下公交占机动化是 66.9% / 66.9% / 67.5%，差不到一个点，没有可调的东西。

### 11.3 效果

| | 修复前 | 修复后 |
|---|---|---|
| bus | **0** | 91 |
| car | **0** | 19 |
| metro | 121 | 11 |
| 公交占机动化 | **100.0%** | **84.3%**（锚点 47.6%） |
| 被用到的路段 | 44/171 | **61/171** |
| 峰值 v/c（represent=100） | 0.36 | **2.58** |
| v/c ≥ 0.8 的路段 | **0** | **20** |

后三行是对 P1 的直接影响：之前 121 趟机动化出行里绝大多数是地铁，**地铁不占路**，所以 represent=100 时一条路都不会堵。现在这些出行落到公交和小汽车上，拥堵才真正发生。§9.3 那句「按 v/c 标定」到这里才有对象。

### 11.4 剩下的缺口属于建模，不属于 bug

84.3% 对 47.6%，公交仍然偏多、小汽车偏少。原因是**小汽车的选择里完全没有拥车条件**——现在纯按距离，6–10 km 且地铁不可达就开车。真实的县城小汽车分担率由家庭拥车率决定，而人口合成器已经有收入数据。

这是加一层机制，不是修一个 bug，应该单独一轮，并且按机制来源标为 (b)/(c) 类。

顺带记一笔：`choose_transport_mode` 用**直线距离**决定方式，`travel_plan` 用**路网距离**计时计价。不一定错（人对「有多远」的感觉本来就粗），但两个距离口径并存，改阈值时容易算错账。

## 十二、§9.4 第 1 条查错了：地图尺度不是问题（2026-09-19）

**只做了测量，没有改任何默认值。**

### 12.1 地图没有偏小

节点同时带 `lat/lng` 和 `x_km/y_km`。随机取 400 对节点，把地图距离和经纬度 haversine 距离相比：

```
地图距离 / 真实距离: 中位 1.000  均值 0.999  min 0.997  max 1.002
东西跨度 18.81 km（经纬度） vs 18.46 km（地图 x）
```

坐标是对的，误差 0.3% 以内。`data/citymap.md` 覆盖 lat 30.28–30.42、lng 120.17–120.36，**是杭州滨江一带真实的约 19 × 15 km**。§9.4 第 1 条「地图空间尺度不足」是误判：短通勤不是地图小造成的。

### 12.2 卡住中位通勤的是工作地的距离衰减

分两层查。先放开候选池（`home_candidates` 12→20 用满全部住宅节点，`workplace_candidates` 8→11 用满全部商业节点）：

| | 12/8（默认） | 20/11 |
|---|---|---|
| 通勤中位 | 3.02 km | **3.02 km** |
| p90 / max | 7.14 / 11.8 | 8.55 / 15.96 |
| 被用到的路段 | 61/171 | 78/171 |
| car | 19 | 36 |
| 公交占机动化 | 84.3% | **66.0%** |

**中位数纹丝不动**，动的是尾部、路网覆盖和方式分布。原因是原来 `top_k=12` 在距中心 3.06 km 处截断，20 个住宅节点里有 8 个从不入选——放开之后住得远的人出现了，但大多数人仍然就近。

真正推动中位数的是工作地的 `distance_decay`（候选固定 20/11）：

| decay | 通勤中位 | 均值 | 自由流通勤(min) | 机动化占比 | 公交占机动化 |
|---|---|---|---|---|---|
| 1.5（默认） | 3.02 km | 3.90 | 18.7 | 32.0% | 66.0% |
| 1.0 | 3.27 | 4.28 | — | 39.3% | 57.7% |
| 0.5 | 3.90 | 4.83 | 22.3 | 47.7% | **57.0%** |
| 0.0 | 5.01 | 5.51 | 25.5 | 57.4% | 58.9% |

单调、干净。顺带注意公交占机动化在 57–59% 触底，无论怎么调空间参数都到不了 47.6% —— 印证 §11.4：**剩下的缺口是拥车条件，不是空间**。

### 12.3 通勤时长锚点：v/c 是独立约束

自由流通勤从 12.9 分钟（§9）涨到 18.7–25.5 分钟。34.5 分钟的锚点现在**原则上够得着了**，但只能靠 `distance_decay` × `agents_represent` 两个旋钮凑，而 v/c 给了一个独立的否定：

| decay=0.5 | 通勤均值 | v/c 中位 | v/c 峰值 |
|---|---|---|---|
| represent=100 | 23.9 min | 0.50 | 2.07 |
| represent=400 | 37.2 min | — | 8.27 |

represent=100 是一座说得通的城（中位 v/c 0.5，最堵的一条走廊 2.07）。要把通勤拉到 34.5 分钟需要 represent 约 300，中位 v/c 会越过 1.2、峰值到 5 以上——**那不是一座城，那是全城瘫痪**。

所以剩下的约 10 分钟缺口，既不是拥堵，也不是地图尺度。候选解释有两个，都还没验：出行距离仍短于真实口径（中位 3.9 km，杭州全市口径约 8 km）；以及 40% 的出行是 20 km/h 的电动车。

### 12.4 需要决策的方法学分叉

`distance_decay` 是引力模型的参数，**拿观测到的通勤距离分布去标定它是这个领域的标准做法**，不是循环论证。但标完之后有一条必须认：

> 一旦按通勤分布标定了 decay，**通勤分布本身就不再是证据**。

所以建议：

1. **候选池已改（本轮落地）**：`home_candidates` / `workplace_candidates` 默认由 12 / 8 改为 **0 = 不设上限**。不写死 20/11，因为那是这张图的节点数；真正的空间限制是搜索半径与引力权重，固定 top-k 只是在第 k 近的那个节点碰巧所在的距离上划一刀。实测效果比 20/11 更好：

   | | 12/8（旧默认） | 0/0（新默认） |
   |---|---|---|
   | 最大居住地占比 | 15.4% | **10.9%** |
   | 最大工作地占比 | 13.3% | **9.1%** |
   | 被用到的路段 | 61/171 | **80/171** |
   | car | 19 | 42 |
   | 公交占机动化 | 84.3% | **62.8%** |
   | 通勤中位 | 3.02 km | 3.17 km |

   中位数基本不动（+0.15 km），所以这一步不构成对通勤锚点的拟合。
2. **`distance_decay` 不要按「命中 34.5 分钟」去标**。若要标，应该用一个结构性判据（例如区内通勤与跨区通勤的占比，如果拿得到这个口径的数据），而不是用同一个被当作结论的量。
3. 无论怎么定，`distance_decay` 都进 provenance 表标 **(c) 类**，由它支撑的空间结论不得单独立论——和 `agents_represent` 同级。

## 十三、模式阶梯：判据、改写，以及一个欠定的结果（2026-09-25）

### 13.1 判据：两个锚点联立，而不是盯着一个

47.6% 单独一个数**可以被作弊**——把公交砍一半就命中了，方向还是错的。Bench 设计 §49
里其实有第五个锚点一直没被用：**绿色出行 >70%**（杭州交通局 2024，与 47.6% 同源）。
两条联立就互相夹住：

```
① T/(T+P) = 0.476   →  P = 1.101·T
② (A+T) ≥ 0.70      →  A ≥ 1.570·T
```
（A=主动出行，T=公交，P=私人机动）

| | 改前 | 目标区间 |
|---|---|---|
| 主动出行 | 65.9% | 54–62% |
| 公交 | 27.5% | 18–22% |
| **私人机动** | **6.6%** | **20–24%** |
| 绿色出行 | 93.4% ✓ | 76–80% ✓ |
| 公交占机动化 | 80.5% ✗ | 47.6% ✓ |

这两个锚点**都没参与过任何标定**（`distance_decay` 按通勤距离定，拥车 pivot 按拥车率定），
所以按机制来源表的规矩它们此刻仍是合法证据。

### 13.2 改写：广义出行成本

`choose_transport_mode` 原本是按距离查表定**一个**模式，汽车分支只存在于 6–10 km 那一带，
所以**有车的人跑 3 公里也不可能开车**——拥车条件只能从那一带里减汽车，永远加不出来。

改成对每个可行模式算广义成本取最小：

```
广义成本 = 出行时长 + 票价 / 时间价值 + 不适惩罚
时间价值 = 月收入 / (8×22) × 0.5 / 60   (元/分钟)
```

这是离散选择的标准形式（(b) 类），而且把刚接通的收入用在了它真正该起作用的地方：
高收入者打车，低收入者骑车路过。可行性直接由条件给出——没车不给 car，地铁不可达不给
metro，没人走 30 公里。确定性靠固定的平局顺序保证。

### 13.3 结果：95% 电动车——不是 bug，是暴露了一个假设

| | 主动 | 公交 | 私人 | 绿色 | 公交占机动化 |
|---|---|---|---|---|---|
| 旧阶梯 | 65.9% | 27.5% | 6.6% | 93.4% | 80.5% |
| 广义成本 | **98.5%** | 0.6% | 0.9% | 99.1% | 40.0% |

中位收入者 3 公里通勤的成本拆解：

| 模式 | 时长 | 票价 | 票价折时 | 不适 | 广义成本 |
|---|---|---|---|---|---|
| e-bike | 10 | 0.3 | 1.3 | 1.0 | **12.3** |
| bike | 15 | 0.0 | 0.0 | 2.0 | 17.0 |
| car | 11 | 1.8 | 7.7 | 3.0 | 21.7 |
| metro | 13 | 2.0 | 8.6 | 3.0 | 24.6 |
| bus | 16 | 2.0 | 8.6 | 4.0 | 28.6 |

模型内部完全自洽：电动车快（20 km/h，比公交的 18 还快）、几乎免费、不用等。
它暴露的是——**仿真默认每个居民都有电动车**。汽车拥有权已经建模，两轮车拥有权没有。
旧阶梯把这个假设藏在距离带里：1.2–3.2 km 一律判 e-bike，那个"带"其实在替代一个
拥有权/可达性条件。这与 §11 的 `route_uses_metro` 是同一类问题：**一个结构选择在替
一个未建模的条件打工。**

### 13.4 为什么没有继续调参，以及默认关

七个不适参数对三个分担率，**严重欠定**。硬调能命中，但那会一次性消耗掉这两个锚点，
并且得到的是一组无法验证的数。所以：

- **代码保留，默认关**（`mode_choice.scored: False`）。
- 它已经交付了一个确定的结论（§13.3 那个假设），这本身比一个凑出来的分担率有价值。
- **要识别这七个参数，需要按距离分段的方式分担率表**（出行调查口径），而不是几个总量。
  在拿到之前，这一层不应打开。

### 13.5 下一件事

两轮车拥有权。它与拥车条件同构，数据同样已经接通（收入、年龄），而且它是当前
**唯一一个能同时把主动出行压下来、把公交和私人机动抬上去**的机制——正是三元组要的方向。
做完再重开 §13.4 的评估。

## 十四、两轮车拥有权：改动正确，锚点仍打不中（2026-09-25）

### 14.1 锚点

- 全国电动自行车保有量 **>4 亿辆**（2024）对约 14.1 亿人 ≈ **0.28 辆/人**（含老幼）。
  通勤年龄段高于这个全人口数。默认参数给出通勤者 **55%** 两轮拥有率。
- 顺带的独立印证：杭州 **人口 1262.4 万 / 机动车 479 万** ≈ 0.379 辆/人，
  与 §13 标定的 34.7% 按人计拥车率同量级。

这两个数让两轮/汽车拥有权从 (c) 升到 **(b)**，不再是凭空的旋钮。

### 14.2 改动

`assign_car_ownership` 与新的 `assign_two_wheeler_ownership` 共用 `_assign_ownership`：
同一个 log 收入 logistic，两轮车的 pivot 远在中位数之下、曲线更平（便宜品）。
`CarOwnershipPlugin` → `VehicleOwnershipPlugin`，两种拥有权各有开关。

**旧阶梯也跟着改了**：1.2–3.2 km 一律判 e-bike 的那个带子，正是这个假设的藏身处。
没有两轮车的人现在落到 bus / walk。**这改变了默认行为，旧 run 不可比。**
没有 `has_two_wheeler` 字段的老语料按 `True` 回落，行为不变（有测试锁住）。

### 14.3 结果：方向全对，三个目标仍拼不齐

| | 主动 | 公交 | 私人 | 绿色 | 公交占机动化 |
|---|---|---|---|---|---|
| **目标** | 54–62% | 18–22% | 20–24% | 76–80% | 47.6% |
| 旧阶梯（全员有两轮） | 65.9% | 27.2% | 6.9% | 93.1% | 79.6% |
| 旧阶梯 + 两轮拥有权 | 43.8% | 49.2% | 6.9% | 93.1% | 87.6% |
| 广义成本（全员有两轮） | 98.5% | 0.6% | 0.9% | 99.1% | 40.0% |
| 广义成本 + 两轮拥有权 | 72.5% | 20.8% | 6.6% | 93.4% | 75.8% |

扫 pivot 的证据更直接：两轮拥有率压到 **10.9%** 时，**私人机动 23.0% 与绿色 77.0%
双双落进目标带**，但主动出行掉到 40.5%（目标 54–62%），公交占机动化仍 61.4%。
**没有任何一个取值能同时满足三条**——三个目标要求的方向互相冲突。

### 14.4 缺的那一块，现在有形状了

扫描里出现 **walk 99 趟**。中位通勤 3.17 km 正好卡在步行 3 km 上限附近，而步行在广义
成本里几乎免费（票价 0、不适 0）。**开放模式的不适没有随距离累积**：走 2.9 公里和走
300 米的代价几乎一样。

这就是 §13.4 说的「需要按距离分段的分担率表」才能定的那组参数——现在不再是抽象结论，
而是一个具体形状：**不适必须是时长的函数，而每分钟不适的量级只能由分距离的方式分担
率来识别。** 三个总量数字给不出它。

### 14.5 判断

连续两轮（拥车、两轮车）都是「改动正确但打不中锚点」。这不是失败，是同一个结论被
两次独立确认：**当前这组已发布的分担率数字，不足以识别一个模式选择模型。**

因此在拿到分距离口径之前：

- 广义成本模型保持默认关。
- 两条拥有权保持默认开——它们各自有锚、各自修掉一个未建模条件，与能否命中分担率无关。
- Track A 的两个通勤锚点在机制来源表里维持「不可用于立论」。

## 十五、锚点和仿真不在同一个宇宙里（2026-09-25）

去查「分距离段的方式分担率」能不能拿到，结果没拿到那个，却拿到了两个一直没有的
**空间锚点**，而它们把前面十四节的困惑一次性解释了。

### 15.1 那份数据不公开

- **浙江省城市公共交通分担率调查**（国家统计局挂网的 2024 年方案）：只调查「出行次数
  及方式」和满意度，**不采集出行距离**，更没有分距离段的方式结构；且方案原文写明
  「调查结果提供给浙江省交通厅使用，**不对外公开**」。
- **《2024 年度中国主要城市通勤监测报告》**（中规院 × 百度地图，PDF 公开）：12 项指标
  全是通勤的时间、空间、轨道/公交覆盖，**明确不含按距离分段的方式结构**。

→ §13.4 / §14.4 需要的那组数据，**公开渠道拿不到**。广义成本模型维持默认关的判断不变。

### 15.2 但拿到了两个新锚点

同一份报告给出杭州（2023）：

| 指标 | 杭州 |
|---|---|
| 单程平均通勤**距离** | **8.1 km** |
| **5 公里以内**通勤比重（幸福通勤） | **52%** |
| 45 分钟公交服务能力 | 48% |

距离锚点是全新的：此前只有通勤**时长** 34.5 min，而时长同时受距离和方式速度影响，
没法单独判断空间层。距离直接判空间层，且**不消耗**任何方式分担率锚点。

### 15.3 扫描结果：近场对得上，尾部够不着

| `distance_decay` | 通勤均值 | 中位 | 5 km 以内 |
|---|---|---|---|
| **锚点** | **8.1 km** | — | **52%** |
| 1.5（当前默认） | 4.10 | 3.17 | 71.6% |
| 0.5 | 5.22 | 4.17 | 57.7% |
| **0.25** | 5.63 | 4.61 | **52.3% ✓** |
| 0.0（无衰减） | 5.94 | 5.46 | 46.5% |

**5 公里以内比重可以命中，均值怎么调都够不着。** 即便完全去掉距离衰减，均值也只有
5.94 km。原因是分布的**尾部**：这张图东西跨度 18.8 km，路网最长通勤约 20.7 km，
而 8.1 km 的均值需要一条长得多的尾巴。

### 15.4 真正的结论：§12 的判断对了一半

§12 说「地图尺度不是问题」——**坐标是对的，这部分没错**（与经纬度 haversine 误差 0.3%）。
错的是下一步推论。正确的说法是：

> 地图覆盖的是杭州滨江一带约 **19 × 15 km 的一个片区**；
> 而这些锚点是**全杭州口径**。两者不是同一个统计总体。

一个半数通勤在 5 公里以内的**片区**，本来就应该比全市有更多的步行/骑行、更少的小汽车。
所以前面十四节里「改动正确但打不中锚点」的反复出现，很可能**不是模型偏了，是拿错了尺子**。

### 15.5 两条路，必须先选一条

**A. 换成全市口径的地图。** 锚点立刻适用，34.5 min / 8.1 km / 52% / 47.6% / >70% 五条
可以一起用。代价：地图、人口、所有标定重来；而且 OSM 全市路网的规模对当前实现是未知数。

**B. 留在片区，换掉锚点。** 承认当前这组锚点不适用于片区，去找片区口径的参照
（如滨江区交通年报），拿不到就把 Track A 的通勤类锚点全部降级为「上下文指标，不作判据」。

在选定之前，**不应该再用这些锚点去标定任何参数**——这正是 §14.5 那句「不用重想目标，
该换的是数据」的修正：**目标本身也要重想，因为它描述的不是我们在仿真的那个东西。**

## 十六、Track B 的双峰：按构造就不可能涌现（2026-09-25）

转 Track B 的第一件事是找真实 run 的数据。结论是两个，都在花 LLM 预算之前拿到。

### 16.1 `output/records/` 里的不是 run，是测试

`traffic.tick.jsonl` 有 378 条、时间戳当天，看上去像一次真跑。实际是
`_day: 0`、`_time: ""`、边名 `Alpha||Beta`——**我自己测试的 fixture**。
`Recorder` 默认写 `output/records`，而用真 kernel 发 `on_time_tick` 的测试就会往
真实产物里追加。`travel.depart.jsonl` 同样是测试数据（`home_node: "Alpha"`）。

已修：测试的 recorder 指向临时目录，并加回归测试锁住"不写进仓库 output"。
`travel.*` 是另一个子系统的同类问题，没动，但值得一并查。

**这条本身就值回票价**：再晚一点，就会有人（包括我）拿这些行当成运行结果去分析。

### 16.2 双峰不是"还没跑出来"，是跑多少次都不会有

查 `generate_daily_routine`（`generative_city_sim.py:1677`）、`sim/_schedule.py`、
`sim/_cognition.py`：**日程生成全程不读通勤时长，也不读拥堵。**
`grep travel_minutes|travel_plan|congestion` 在这三处零命中。

所以：

- 早晚高峰如果出现，来自 profile 散文（「工作日节奏规律，通勤与工作占据主要时段」）
  和日程提示里的工作日/周末规则——**是被告知的，不是涌现的**。
- 更关键：**没有任何机制能让它涌现**。高峰展宽（堵→提前出门）需要拥堵反馈进日程，
  这条路不存在。跑 30 天和跑 300 天结果一样。

按机制来源表的规矩，双峰属于 **(c) 类且由输入决定**，不能作为 Track B 的证据。
§13.1 里我把它列为"唯一没被消费过的判据"——**那是错的，它从来就不是判据。**

### 16.3 该换成哪个 stylized fact

Track B 要的是经 agent→环境→agent 回路产生的规律。当前**真正闭合**的回路只有一条：

> 节点占用 → 拥挤感知 → 中断/改址 → 空间规避偏好（P0–P4）

这条链上没有任何文本在告诉 agent「要避开拥挤的地方」，规避分是从亲历的异常里累出来的，
且跨天衰减、跨运行持久化。**它产生的聚集-疏散再分布才是当前唯一够格的 Track B 候选。**

判据形状（已实现，见 16.4）：
- 关掉 `spatial_preferences` 跑一次作参照，开着跑一次；
- 比较热门地点访问量的基尼/赫芬达尔随天数的变化；
- 判据是**两条曲线的分离**跨种子稳定，而不是某个绝对值——与 group agent 的 L1/L2 同逻辑。

这条需要真跑，但它值得跑：有机制、有对照、判据是相对量。双峰不值得，因为跑之前就知道
答案。

### 16.4 harness 已搭好，跑法如下（2026-09-25）

三件东西落地，都不花 LLM 预算就能验：

| 件 | 位置 | 验证 |
|---|---|---|
| 占用记录 | `local_physical.record_occupancy`（默认关）→ 每 tick 一行 `spatial.occupancy` | `tests/test_occupancy_recording.py` 4 passed |
| 分析器 | `benchmark/trackb_spatial.py` | `--self-check` 输出 `even 0.100 / lumpy 0.829`；`benchmark/test_trackb_spatial.py` 12 passed |
| 判据 | 两臂每日赫芬达尔曲线的**分离量** vs 跨种子标准差的 `2.0` 倍，取后半程，要求 ≥3 个种子 | 同上 |

**跑法**（每臂每种子一次，共 6 次）：

```bash
GAWORLD_CONFIG_OVERRIDES='{"random_seed":1,"stateful":false,
    "local_physical":{"record_occupancy":true},
    "spatial_preferences":{"enabled":false},
    "records":{"output_dir":"output/trackb/ref-s1"}}' \
  python generative_city_sim.py run --sim-days 30
# …"enabled":true → trt-s1；再换 random_seed 2、3

python benchmark/trackb_spatial.py \
    --reference output/trackb/ref-s{1,2,3} \
    --treatment output/trackb/trt-s{1,2,3}
```

**两个坑，写代码时才查出来的，都会静默毁掉实验：**

1. **`stateful` 必须设 false。** `env_preferences` 会存进
   `memory_dir/agent_<id>_env_preferences.json`，并在 `agents.built` 时读回
   （`world/plugin.py:196,205`）。默认 `stateful: true`，于是处理臂的种子 2
   是从种子 1 的沉积开始跑的——跨种子标准差就不再是任何东西的噪声估计。
   （`settings/environment.py` 里那条「In-memory across a run」的注释已经过期，
   持久化后来加上了。）
2. **不能用 `--fast-forward` / `--sim-months` / `--sim-years`。** 这三个把日内
   tick 循环换成"每 agent 每步一条 brief"，而占用是按 tick 记的——记不到。

**先花两分钟做管道冒烟测试**：加
`"fos_fast_mode":{"deterministic_cognition":true}` 配 `--sim-days 2` 跑一次，
确认 `spatial.occupancy.jsonl` 非空，再开真跑。

**这次没跑。** 真跑要 LLM 预算，等你确认。harness 本身的正确性不依赖那笔钱——
判据逻辑、噪声门槛、占用记录都已经各自被测试锁住了。

### 16.5 试跑：两个会让实验白跑的东西，和一个真正的拦路虎（2026-09-25）

按 16.4 的跑法开了两次试跑（`benchmark/run_trackb.sh` + 一次 100 人 2 天的探针），
没跑完就停了，但拿到三个结论。

**第一个：`dashboard_config.json` 里 `agent_ids: [12]`、`sim_days: 5`。**
照 16.4 原样启动，跑的是**一个居民**。拥挤是"占用/容量"，一个人挤不出任何东西——
不会触发中断，不会累出规避分，两臂结果会完全一样，而原因和假设毫无关系。
这条比 §16.1 的测试污染更阴，因为日志里什么都不报，只有一行
`derived capabilities for 1 agents` 一闪而过。
已修：`run_trackb.sh` 用 `N`（默认 100）显式铺 `agent_ids = 1..N`，并把人数打进每行
run 标题。**CONFIG 默认是 5 个人，dashboard 会留下 1 个人——这个键必须显式写。**

**第二个：当前配置的城市是芝加哥（100 人），不是乌镇（63 人）。**
§15 那套「19×15 km 城区 vs 全市锚点」的讨论是针对乌镇的地图说的；Track B 换城了，
判据是相对量所以不受影响，但别把两边的数字混着引。

**第三个（真正的拦路虎）：整条仿真串行卡在 LLM 上。**
探针跑了 9 分 46 秒，CPU 时间 **6.5 秒**——`%CPU 0.0`，`lsof` 显示始终只有
**一条** ESTABLISHED 的 443 连接。也就是说 99% 的墙上时间在等
MiniMax-M3 的一次回包，而且是一次一个。观测到两次 4–5 分钟的单次调用停顿；
100 人的 setup 阶段（还没进 tick 循环）就没在 15 分钟内走完。

按这个速率，「6 次 run × 30 天 × 100 人」不是预算问题，是量级问题：
setup 一项就要小时级，tick 循环的 agent-day 数是 setup 的几十倍。

**顺带一个与实验无关但影响所有 run 的问题**：第一条 LLM 日志就是
`LLM output was truncated by max_tokens=512`，而 `schedule` 任务路由到的正是这个
provider。日程解析看到的是被截断的畸形输出——它会静默回落到通用行为
（日志里另有 `action space generation produced nothing for agent … — falling back`）。
这条不修，Track B 跑出来的日程质量本身就要打问号。

**所以没有继续跑。** 需要你定的是吞吐，不是钱：给这个 provider 提高 `max_tokens`
并确认并发/限流，或者把这次实验路由到本地 `gemma4-12b`（Track B 要的是大量
agent-day，不是最好的认知质量——代价是要在结论里写明认知模型不同），
再或者压横跨（种子 3→3 不能少，天数 30 可以谈，人数 100 不能少）。
`run_trackb.sh` 是可续跑的：算完的 run 会跳过，改完配置接着跑就行。

### 16.6 吞吐查清楚了：不是 API 慢，是整条 tick 循环没有并发（2026-09-25）

**先推翻了一个自己的猜想。** 16.5 里我把 4–5 分钟的停顿记在了
“provider 慢”头上。拿 `probe_provider` 直接打一发：

| max_tokens | 往返 |
|---|---|
| 512 | 1539 ms |
| 2048 | 824 ms |

**端点本身是健康的。** 那些分钟级停顿来自 512 截断后的重试
（`attempts=3`）加长生成，不是网络。已改：`dashboard_config.json` 的
MiniMax-M3 加上 `max_tokens: 4096` 与 `timeout: 180`（原文件备份在
`output/trackb/dashboard_config.bak.json`）。改完再跑，单次调用均值 **2.4 s**，
再没出现过分钟级停顿。

**真正的瓶颈在别处。** 5 人、DEBUG 日志、跑到第 1 天第 3 个 tick：

- LLM 调用 **198** 次，占墙上时间 **8.0 分钟**（全程约 90%）；
- 拆开：初始化 2.0 次/人，tick 循环 **7.0 次/人/tick**，其中 `actions` 占大头；
- 整个跑程里没有一条并发日志。

**这里我又错了一次，写下来当教训。** 我先 grep 了
`ThreadPool|ProcessPool|as_completed`，只搜 `generative_city_sim.py` 和
`gaworld/sim/`，零命中，就准备下“主循环根本没有并发”的结论。
实际上 `generative_city_sim.py:19` 就写着
`from gaworld.core.runner import parallel_map, resolve_max_workers`——
并发早就接好了，只是默认关着，而我搜的是实现细节而不是调用点。

**真实情况**：`gaworld/core/runner.py` 提供 `parallel_map`（按输入顺序返回结果，
`max_workers<=1` 时不开线程池），两个调用点都在主循环：
`generative_city_sim.py:4146`（每人一次的 digest）和 `:4552`（每日日程生成）。
**后者包括 `ensure_action_space_for_activity`，也就是开销大头 `actions`。**
闸门是 `CONFIG["concurrency"]`，默认
`{"enabled": false, "day_routine_workers": 1}`——所以上面那 168 小时量的是
**默认配置**，不是能力上限。

实测（开 `{"enabled": true, "day_routine_workers": 8}`，5 人）：
`parallel_map(day_routine) parallel n=5 workers=5`——闸门生效，workers 被人数截住。
100 人时它就是真的 8 路并发。

`WorkerPool(workers=2)` 是 `gaworld/work/` 那套接单适配器的，不管 tick 循环；
`gaworld/parallel/runner.py` 是并行跑**多个世界**，单个世界内部另论。

粗估（取 12 tick/天，2.4 s/调用，线性扩到 100 人）：

| 规模 | 单跑墙上时间 |
|---|---|
| 100 人 × 1 天 | ≈ 5.6 h |
| 100 人 × 30 天 | ≈ 168 h |
| 6 跑串行 | ≈ 1000 h |

换天数改不了量级，换人数会把拥挤机制本身弄没。**能改量级的只有并发——
而并发不用新写，只用打开。**

代价写在 `core/runner.py` 的 docstring 里，不能装作没看见：`max_workers>1` 时
全局 `random` 的消耗顺序不再确定，**同种子不再严格复现**。对 Track B 可接受，
因为判据本来就是“两条曲线的分离 vs 跨种子标准差”，多出来的这部分拖动会被
分母吸收；但它对**任何需要逐步复现的实验不可接受**，写结论时要说明这一条。

`fos_fast_mode.deterministic_cognition` 不是这把钥匙：它只接管
perception / planning / reflection，而开销大头 `actions`、`schedule`、
`daily_routine`、`daily_intentions` 一个都没盖到。

**下一个要测的数（正在跑）**：`actions` 看起来有缓存（日志里有
“falling back to generic behavioural actions (**not cached**)”）。如果 7 次/人/tick
是冷缓存数字、跑几天后掉下来，上面那张表就要重算。这是决定“168 小时”还是
“十几小时”的分水岭，而它只需要 5 人 × 3 天就能测出来。

### 16.7 并发闸门一打开就崩（现存 bug，不是 Track B 特有）（2026-09-25）

按 16.6 的结论开了 `{"concurrency": {"enabled": true, "day_routine_workers": 8}}`，
5 人跑。`parallel_map(day_routine) parallel n=5 workers=5` 正常打印，紧接着整个
进程挂掉：

```
File "generative_city_sim.py", line 4530, in _compute_daily_routine
File "generative_city_sim.py", line 1719, in generate_daily_routine
File "gaworld/memory/store.py", line 825, in retrieve_relevant_memories
File "gaworld/memory/store.py", line 684, in vector_db_search
sqlite3.ProgrammingError: SQLite objects created in a thread can only be
used in that same thread.
```

`store.py:412` 整个模块共用一个全局连接
`sqlite3.connect(VECTOR_DB_PATH, timeout=30)`，没写 `check_same_thread=False`，
所以它绑在建立它的线程上。

**`:4524` 那段注释推错了一个地方**。它写的是“Per-agent IO
(save_agent_actions, log writes) is left in the serial merge phase below to keep
the SQLite + log file writers single-writer”——它盯着的是**写**。真正碰
SQLite 的是**读**：`generate_daily_routine` 会去召回相关记忆，而这步就在并行
那一段里。所以这个闸门从来没在真跑里被打开过（打开就崩）——但它在配置面板里
有名字、有中英文帮助文案，看上去就像一个可用选项。

**范围**：这不是 Track B 的问题。任何人打开这个闸门都会在第一天的日程生成处崩掉。

**已修，但不是我最初那个改法。** 我先按“最小改动”加了
`check_same_thread=False`（该机器 `sqlite3.threadsafety == 3`，Python 3.12.9 /
SQLite 3.45.3，模块是 serialized 的），再给三个写点加一把锁。
`ProgrammingError` 没了，换成了：

```
sqlite3.InterfaceError: bad parameter or other API misuse
```

并发读在同一个连接上互相踩游标状态。“模块是 serialized”保的是模块，
不保一个 Connection 被多线程同时跑语句。

**改成每线程一个连接**（`threading.local()`，另存一份连接名单供 teardown
全部关掉）。这反而更简单：锁不需要了，`check_same_thread` 也不需要了，
而 `with conn:` 终于名副其实——只提交本线程自己的事务。WAL 负责让它们共享
文件。

回归测试：`tests/test_vector_db_threading.py`（主线程建库、worker 线程读写）。
它把两个坏版本都拦下来过：未修时 `ProgrammingError`，只加
`check_same_thread=False` 时 `InterfaceError`。记忆层相关 94 条测试全绿。

真跑验证：`parallel_map(day_routine) parallel n=5 workers=5` 之后顺利进入 tick
循环并写出占用行，日志里再无 SQLite 异常。

**不要把这当成提速结论。** 5 人规模下并行版并不比串行版快（同等壁上时间内
occ=2 vs 4）：workers 被 n=5 截住，而 setup 和逐 tick 的那部分依旧串行。
并行只盖了 digest 和日程生成两个阶段。**100 人下的实际加速比还没测过**，
16.6 那张时间表在测之前不能按“除以 8”来改。
