# 时间合理性层（2026-10-26）

状态：已实现。
代码：`gaworld/sim/_timefit.py`（时段表与判定原语）、
`gaworld/sim/_schedule.py`（`build_schedule_map` 入口的日程修复）、
`gaworld/sim/_action.py`（动作层面的时段降权）、
`gaworld/sim/_step.py`（临时改程的时段闸门）。
配置：`CONFIG["time_plausibility"]`（`gaworld/settings/runtime.py`，默认开启）。
测试：`tests/test_time_plausibility.py`。
可比性版本：Epoch 12。

---

## 1. 为什么

仿真里居民会做出与钟点不符的事。最常见的一类是**时段错位**：

* 清晨六点「收尾今天的工作，整理明日计划」；
* 早上八点半「在托管班食堂和搭班们一起吃工作餐」；
* 凌晨三点还在「处理待办」。

这类问题不是提示词能根治的。原因有三个：

1. **提示词只是建议。** 改程决策器、感知与计划的提示词里都带着当前时间，模型仍然
   按句子要写的东西走——「收尾工作」这个动作本身没有错，错的是它出现的钟点。
2. **动作空间是按「活动」生成的，不带时间。** 「上午工作」这个活动对应一整套动作，
   里面既有「继续跟进手上的项目」也有「收尾今天的工作」，两者的合理时段完全相反，
   而动作空间是缓存下来整天复用的。
3. **日程本身就没有时钟。** 模型给日程写「时间 + 活动」，两者是否对得上从没有被检查过；
   模型把工作餐排在 08:32，仿真照单全收。

已有的合理性检查都在别的维度上：地点有营业时间（`gaworld/world/city_map.py`），
事件有严重度，居民状态有疲劳与饥饿。**唯独「这件事在这个钟点合不合理」没人管。**

## 2. 做了什么

### 2.1 一张时段表

`gaworld/sim/_timefit.py` 里是一张粗粒度的表：每条规则给一个关键词集合和一组
「合理时段」（分钟制，窗口不跨零点，睡眠用两个窗口表示），外加一个灰区宽度。

* 夜间睡眠 21:30–05:00 · 午睡 11:30–16:00 · 早饭 05:00–10:00 · 午饭 10:30–14:30 ·
  晚饭 16:30–21:00 · 通勤 05:30–10:30 / 16:00–20:30 · 工作 07:30–19:00 ·
  加班 17:00–22:30 · 收工 17:00–23:00 · 运动 05:00–21:30 · 育儿 07:00–20:00 ·
  办事 07:00–21:00 · 购物 07:00–22:00 · 家务 05:00–23:00 …
* 动作表是另一套更细的：收尾 / 收工 / 下班 / 总结今天 → 下班前后；晨会 / 开工 / 打卡 →
  上午；午休 → 中午；夜跑 → 傍晚以后；跑步 / 散步 / 健身 → 05:00–21:30。

匹配方式是**最长关键词优先**：「工作餐」（3 字）压过「工作」（2 字），所以工作餐按
午饭算，不会被当成工作；「夜跑」压过「跑」。另有 `exclude` 词表处理同字不同义：
「跑流程」「跑数据」里的「跑」不是跑步。

### 2.2 判定只有四档

`ok`（在正常时段）/ `soft`（灰区，允许）/ `bad`（离谱）/ `unknown`（表里没有的
自由文本，**一律放行**——不认识的东西不判死，否则大部分真实行为都会被误杀）。

### 2.3 三个接入点

| 层 | 接入点 | 做法 |
|---|---|---|
| 日程 | `gaworld/sim/_schedule.py::build_schedule_map` | 每天的日程（第一天的原型与之后每天生成的日程）都从这里进入仿真。在这里把「时间与活动对不上」的项挪回它的合理窗口。 |
| 动作 | `gaworld/sim/_action.py::choose_action` | 不合时机的动作被**降权**（`soft` −0.35，`bad` −2.0），不是删除。冲动分支（`random.choice`）也会先剔除离谱项。 |
| 改程 | `gaworld/sim/_step.py::_accept_activity_change` | 模型临时改程提出的新活动要过时段闸门；不成立就退回原计划。 |

`build_schedule_map` 原本在 `generative_city_sim.py` 里，这次移进 `gaworld/sim/_schedule.py`
（该文件有「只减不增」的行数预算），并成为时间修复的唯一入口。

### 2.4 随机性被保留，但被关进笼子

用户的要求是「可以有随机性，但随机性要在合理范围内」。做法是**降权而不是禁止**：

* 清晨六点的「收尾今天的工作」权重被压到约 1/20——不是 0，所以仍有可能发生；
* 傍晚六点的同一个动作一点不加罚；
* 清晨五点半的「沿着小区跑道跑两公里」完全不受影响——它在合理时段里；
* 改程被拒时留了一个 `deviation_chance`（默认 4%）的例外，让「不合理但偶尔发生」成立。

日程修复同样是**局部**的：一项最多挪 180 分钟，挪不动就留在原处——丢掉居民的一项
活动比留一个偶尔离谱的钟点更糟。夜班居民的日程不会被拖回白天：日程里已经有夜间
工作项时，工作规则对这份日程关闭。

## 3. 边界与代价

* 表是粗的。它判「03:00 上班」离谱，不判「09:40 收尾」离谱。规则写多了会误杀
  真实行为，所以宁可放过。
* `unknown` 是常态：日程里的活动常是长句子（「起床洗漱，戴上耳机听本地教育广播」），
  命中关键字就判，命中不了就放行。
* 快进模式（`gaworld/sim/_fastforward.py`）走的是每日简报，不经过动作选择器，
  这一层对它不生效。
* 生命事件重排当天的日程（`reshape_day_for_life_event`）不受此表约束——半夜送医是合理的。

## 4. 配置

```json
"time_plausibility": {
  "enabled": true,
  "repair_schedule": true,
  "gate_actions": true,
  "gate_activity_changes": true,
  "max_shift_minutes": 180,
  "min_gap_minutes": 15,
  "soft_penalty": 0.35,
  "hard_penalty": 2.0,
  "deviation_chance": 0.04
}
```

`enabled: false` 即回到旧行为（模型自己想什么就是什么）。
