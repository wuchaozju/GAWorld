# 持久组织主体 v1：社区组织与企业

日期：2026-10-03（Asia/Shanghai）  
状态：已实现，通过本地测试与界面验收（模型调用使用 mock）  
已确认的方向：同时做社区资源分配组织与企业，使用共同组织底座。

## 1. 第一版的结果

同一个世界内，组织有稳定身份、目标、负责人、成员、有限预算、版本化决策规则、申请与决策历史。重启仿真或更换负责人后，组织继续存在。组织的决定会实际改变资源、成员或就业关系，而不是只生成一段叙述。

社区组织执行资助申请、审核、分配和支付；企业执行岗位发布、应聘、招聘和工资付款。两类组织使用同一个持久状态与审计协议，各自拥有决策规则。

第一版支持单机逐 tick 和按日快进。月/年快进及分布式世界尚未具备组织结算的对应协议；启用组织时须在启动检查中明确拒绝这些组合，不能悄悄停用组织继续生成看似有效的结果。

## 2. 三种方案与推荐

| 方案 | 能交付什么 | 代价与局限 |
|---|---|---|
| **A：规则决策的持久组织，推荐** | 两类组织、真实预算与执行、稳定历史；居民看得到组织信息并可申请 | 组织决策程序必须明确登记；暂不模拟开放式组织战略 |
| B：只有组织名册与账户 | 创建组织、成员、负责人、余额和历史 | 工程较小，但申请、招聘与分配没有形成可运行过程 |
| C：LLM 驱动的自主组织 | 组织定期开会、讨论战略、选择行动 | 增加调用成本、输出校验与跨模型偏差；规则、账本和持久化仍需先完成 |

采用 A。组织决策零额外 LLM 调用；居民沿现有认知管线选择组织相关行动。后续 LLM 可以提出有限动作，但仍交由同一约束与执行层处理。

## 3. 共用组织模型

### 3.1 身份与成员

- 稳定 `organization_id`，在当前世界/运行目录内唯一；名称变化不产生新身份。
- 类型为 `community` 或 `company`，包含名称、目标、状态、创建时间、负责人和规则版本。
- 成员记录含居民 ID、角色、加入/离开时间与原因。负责人必须是有效成员；退出负责人前先完成交接。
- 居民可加入多个社区组织，第一版最多拥有一个企业雇佣关系。
- 政府或企业部门池不是具体组织；既有部门池继续作为未组织化活动的对手方。
- 居民编号只在本世界有效。持久状态保存人口来源与参与居民指纹；编号复用或人口不兼容时阻止恢复，不能把历史挂到另一人身上。
- 本次没有参与运行的成员保留为不活跃成员，不自动视为离职，不给他们发本次运行的工资或资助。

### 3.2 财务与规则

- 金额按整数分存储；禁止负数、NaN、无限值与越界金额。
- 分开保存可用余额、已承诺但未支付的金额、累计收入、累计支出与工资欠付额。
- 每条规则有名称、版本、参数、生效时间和修改者；历史决策保存当时规则，不能用当前规则覆盖过去。
- 决策读同一批次冻结的申请与居民信息，先生成执行计划，再检查人数、资格和预算。
- 同分候选使用组织自己的稳定种子打破平局，不消耗其他插件的随机数序列。
- 组织关闭后停止新申请与招聘，保留账目、已有义务和历史；第一版不提供抹除历史的“删除”。

## 4. 社区组织试点

### 4.1 行为流程

居民提交资助申请 → 到指定决策日冻结申请与资格 → 按规则决定 → 检查预算 → 支付 → 居民获知结果 → 记录实际执行。

申请记录包括组织、居民、金额、原因、提交时间、状态与请求 ID。允许研究者通过同一命令接口提交实验申请；命令保存来源，区别于居民自己的行为。

### 4.2 两种规则

1. **等额分配：** 对本批次合格申请按相同上限分配；受到各自申请金额及总预算约束，余下款项按确定性分币规则处理。
2. **困难优先：** 先按决策前冻结的 `checking + savings` 从低到高排序，同额再按已登记的同住受抚养人数从高到低排序；仍相同则按组织种子打破平局。依次最多支付申请金额和单人上限，直到预算耗尽。不添加未经说明的复合权重。

同一批次资格与困难信息来自分配前快照，不能让先收到资助的人影响本批次另一人的排序。默认资格是本组织有效成员、年满 18 岁且本批次无已支付申请。规则、资格范围和受助上限均可配置。家庭负担数据不可得时记录缺失并仅按现金排序；现金数据不可得时拒绝困难优先评估，不能按零现金优先资助。

### 4.3 研究输出

申请人数、合格人数、覆盖率、实际资助金额、等待时间、未获资助原因、预算剩余与按预先定义群体的获得分布。拒绝、预算不足和无人申请都是有效结果。

## 5. 企业试点

### 5.1 岗位与招聘

- 企业发布有限岗位，记录职业、人数、工资标准、最低资格与工作地点。
- 居民提交应聘；按固定周期对候选批次评估。
- 第一版提供资格达标后的确定性抽签与技能匹配优先两种规则。默认使用现有 `economy.income_skill`，岗位登记 `min_income_skill`，通过资格后按该分数从高到低排序，同分按组织种子打破平局。该字段是模型内工作能力代理，不宣称等同于现实能力；字段缺失时拒绝技能评估并注明原因，不补成零。
- 录用后更新企业成员及雇佣关系，复用经济模块的就业变更接口同步职业与收入参数。
- 第一版面向无业或主动应聘者；离开旧企业时先解除旧关系。不能同时占用两家企业的全职岗位。
- 岗位不能超额，拒聘保存原因。负责人不能靠自然语言越过已登记的预算和岗位约束。

### 5.2 工资

工资复用现有工作收入核算、税费与带薪休假流程，只改变付款来源：已建立雇佣关系的居民由对应企业组织账户付款，其他居民沿用现有企业部门池。

不是“先从旧企业池发一次，再从组织账户发一次”。招聘、逐 tick 工资、按日快进工资、带薪休假及现有工资型奖金均须明确付款方。投资回报、商户分成等其他收入不能被误认成雇主工资。

企业资金不足时，实际支付不得超过可用余额；未支付部分形成欠薪记录，并向员工展示。第一版不自动创造贷款、注资或破产结果。补充资金后，既有欠薪优先于新自由支出；支付记录仍保留应付与实付。

### 5.3 研究输出

岗位空缺、申请与拒聘、录用、岗位占用、工资应付/实付、欠薪、余额、人员流动与等待时间。首版是有限岗位招聘，不声称已经完成劳资谈判、劳动法或完整产业生产体系。

## 6. 钱从哪里来：组织账户与守恒

现有经济代码 `_record_income` 默认从 `firms` 付款；`_system_total` 对部门字典的全部余额求和，但日审计只有三个固定部门列。组织资金接入必须同时处理付款路由和审计展示。

具体约定：

1. 使用经济侧登记的组织子账户，组织 ID 映射为稳定账户键；运行时余额只有一个权威来源，SQLite 中保存它的持久化状态。
2. 初始资金与后续拨款来自显式声明的 `government` 或 `firms` 部门池，并记录等额借/贷方；组织默认不允许透支。
3. 部门池仍遵循现有允许负余额的规则，因此财政拨款可能体现部门负余额。这是既有宏观账户假设，不等于组织有无限可用预算；界面必须显示拨款来源。
4. 资助属于转移收入，不能自动计作劳动收入或重复进入工资税基。工资继续使用已有劳动收入与税费口径。
5. 组织付款使用经济模块的公共财务接口，不调用跨模块私有记账函数。该接口接受来源账户、用途与幂等交易 ID，返回实际支付与未支付金额。
6. 货币总量包含居民账户、既有部门账户与组织账户。审计增加组织余额合计及组织支付明细，防止新增账户被漏算或算两次。
7. 默认关闭组织时，旧财务路径、随机数调用、审计格式和行为保持一致。

首版不自动补充企业营业收入。企业可通过显式拨款或转入资金获得预算，资金耗尽后的欠薪与停止招聘可观察；企业生产、销售、利润反馈属于后续机制。

## 7. 持久化、续跑与重置

### 7.1 存储

- 权威组织数据库采用标准库 SQLite，位于有效 `memory_dir` 下的 `organizations.sqlite`。现有 reset 清理 memory 时即可同步清除组织状态，避免居民已经重置而组织仍在旧年份。
- 组织种子定义属于输入；世界复制及城市切换按照已有输入隔离约定处理。重新载入种子不得再次发放初始资金或覆盖已存在组织。
- 组织快照和指标导出到有效 `organizations.output_dir`；该路径加入 `city.config.RUN_PATHS`，随城市、用户世界和平行世界重定位。
- 数据库包含组织、成员、岗位、申请、决策、交易、待执行命令、规则历史、执行批次与状态版本。读接口区分当前持久状态和指定运行的记录。
- 记录器输出 `organizations.organization`、`organizations.membership`、`organizations.application`、`organizations.decision`、`organizations.transaction` 和 `organizations.summary`。

### 7.2 续跑语义

- `stateful=True` 正常结束后的下一次运行恢复组织身份、余额、规则、岗位和历史；负责人变更不能清空历史。
- `stateful=False` 是重新开始的实验，不恢复历史组织。输出记录带运行/世代标识，避免把新的 Day 1 与旧 Day 1 混合。
- 组织记录自己的已处理日及批次 ID。同一日边界重复发射不会再次拨款或分配；工资另外使用居民、日/时刻、收入类别与组织 ID 的付款回执防重。恢复时不得回到组织已处理日以前继续结算。
- 改变运行居民子集不会删除其他成员；涉及当前不活跃居民的支付明确等待或拒绝，不临时造人。
- reset 清除组织运行状态与结果记录，种子定义保留；下次运行重新形成新的组织历史。

### 7.3 中断边界

现有居民经济 JSON 和组织 SQLite 不能天然共享一个原子事务，因此不承诺任意时刻崩溃后都能无损自动恢复。

组织执行以持久交易 ID 和执行阶段记录防重复；经济侧付款回执与受款账户一起持久化。重启时只有已核对的回执可以完成待提交交易；缺失、损坏或居民时钟与组织时钟矛盾时标记 `recovery_required`，停止新的组织支付并返回明确错误，不能猜测已支付状态后再发一次。

首版必须保证正常日边界续跑，并测试可识别中断时的防重复或明确拒绝。完整世界检查点、任意 tick 回滚和自动故障修复不属于本功能的隐含承诺。

## 8. 接入架构与操作入口

### 8.1 模块边界

新增 Python 实现放在 `gaworld/organizations/`：模型与校验、SQLite 存储、规则决策、服务与执行、叙述、插件、CLI 分开。插件 ID 为 `organizations`，默认关闭，依赖启用的经济能力。

插件在组织初始化时恢复状态，在日边界处理命令与决策，在居民感知中提供本人的组织、岗位、申请结果和工资情况。成员引用保存在 `ctx.agent_ext(agent, 'organizations')`，世界级状态由该插件管理。

为居民增加可执行的申请/应聘动作，使用候选动作扩展点及受控动作标识；执行器只认经过校验的组织 ID 与请求。自由文字里的“已经录用”“已经收到钱”不会改变账本。现有动作选择器主要从候选集合选动作，只有感知文本而没有候选接入是不完整实现。

新增候选动作或财务付款路由所需的通用扩展点放在 `gaworld/` 的现有管线/财务模块。CLI 入口不加入组织领域内联逻辑。

不支持的配置组合、经济能力关闭、组织状态不兼容必须在创建仿真进程/启动运行之前由明确的配置校验拒绝，CLI 同样调用该校验。不能依赖插件 `setup` 抛错，因为现有插件注册器会捕获错误后仅发警告、停用插件。

### 8.2 写入与并发

- API 只提交持久命令，不直接修改运行中的组织余额、成员或居民状态。
- 仿真进程作为组织状态单一执行者，按日边界应用命令；SQLite 保证命令排队的一致性。
- 组织付款与岗位录用使用独立锁/事务，防止不同居民并发操作超支或超额招聘。
- 未运行时提交的命令显示“等待下一次启用组织的运行”；运行时显示已排队、已应用或拒绝，不能把 202 当成已经执行。
- 一个运行目录只允许一个组织状态执行者；平行实验使用自己的目录，不能共享一份数据库。

### 8.3 用户入口

提供世界内的组织管理入口与 `python -m gaworld.organizations`。首版操作包括组织列表/详情、创建、成员与负责人交接、拨款、申请、岗位发布、应聘、关闭和历史查询。

Dashboard API 使用 `gaworld/apps/organizations_api.py`，通过 `routes.py` 装配，并为所有路由登记 OpenAPI。建议 API 表面包括 `GET /api/organizations`、组织详情/历史查询和 `POST /api/organizations/commands`；命令 ID 可查询状态。

所有读写路径经有效世界配置解析；写权限为当前世界拥有者或管理员，默认共享世界为管理员。居民在仿真内的申请依据世界成员关系校验。创建命令保留账号所有权与审计来源；不允许从客户端参数指定其他世界的输出路径。

管理界面显示两类模板、成员与负责人、资金来源、余额与承诺额、岗位、待处理申请、决策和交易。显示的数字来自实际记录；排队命令与已经执行的结果分别标示。

## 9. 指标与研究范围

首版提供带定义、分母、时间与运行标识的组织指标 CSV/JSON，并支持对照规则的离线比较：预算利用率、资助覆盖率、实际金额、拒绝原因、岗位占用、录用等待、工资实付与欠薪。

已有研究后端主要读取居民状态 CSV。本功能不把新的组织指标冒充已经接入预注册假设评分；首版明确提供原始组织指标和规则对照导出，自动预注册的多来源指标后端另行接入。

示例提供同一人口、同一组织种子和预算下的两套规则配置。它用于观察人工社会内部的制度差异；首版规则及参数属于模型假设，不声称现实政策有效。

## 10. 必须通过的验收

| 验收 | 应看到的结果 |
|---|---|
| 组织身份与负责人交接 | ID、预算和历史延续，成员关系一致 |
| 两种社区分配规则 | 同一申请快照得出可重算的结果，拒绝原因完整 |
| 有限岗位招聘 | 不超额，不重复雇佣；职业与收入状态同步 |
| 工资付款方 | 已雇佣居民只由对应组织付款一次，未雇佣居民沿用旧路径 |
| 预算不足 | 实付受余额约束，欠薪/拒绝明确，没有凭空资金 |
| 货币守恒 | 拨款、资助、工资、税费与休假支付前后总量一致至分 |
| 正常续跑与重复日边界 | 恢复相同组织和余额，已执行批次不重复 |
| 可识别中断 | 已保存回执不重付，矛盾状态明确拒绝继续支付 |
| reset | 居民和组织共同从新世代开始，旧种子不丢失 |
| 世界与平行实验隔离 | 相同组织 ID 在不同目录不会共享余额和历史 |
| 权限与 API | 越权写入拒绝，所有路由有 OpenAPI，命令状态可查询 |
| 关闭功能 | 不新增组织行为/输出，不改变旧财务与随机数路径 |
| 运行方式 | 单机逐 tick 与日快进通过；不支持组合在启动时明确拒绝 |
| 居民行为接入 | 组织信息进入感知，真实申请来自受控动作，故事文字不能伪造支付 |

测试使用临时目录、固定种子和 mock LLM，不访问真实网络。相关回归覆盖经济守恒、就业事件、带薪休假、日快进、世界路径、API 权限及 OpenAPI。实现完成后运行 `pytest --suite core`，再运行目标模块及改动涉及的前端检查。

## 11. 实施顺序

1. 共用模型、存储、命令与恢复规则。
2. 组织账户与公共付款接口、守恒及工资来源测试。
3. 社区申请与两种分配规则。
4. 企业岗位、录用、工资与欠薪。
5. 插件、居民感知与受控动作接入。
