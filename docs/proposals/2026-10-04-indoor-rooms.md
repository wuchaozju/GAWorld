# 室内房间：空间树进入仿真（2026-10-04）

状态：已实现，默认关（`local_physical.rooms.enabled`）。
代码：`gaworld/world/spatial_tree.py`（树、布局、分户、选房间）、`gaworld/world/plugin.py` 的 `RoomsPlugin`
与 `VenueCapacityPlugin`（按房间计容量）、`gaworld/behavior/dynamic.py` 的 `detect_co_located_agents`（同屋才算碰面）。
测试：`tests/test_rooms.py`。

---

## 1. 为什么

室内空间树（`building → room → object`，仿 generative_agents 的 `world:sector:arena:object`）此前只在像素小镇的
`site/simviz/spatial-tree.js` 里：前端按活动猜每个人坐在哪，仿真本身只认到「地点」为止。这带来两个问题：

* **同一栋住宅楼的人在家时都算「在一起」。** 偶遇（`detect_co_located_agents`）只比较 `locations.current`，
  一栋楼住几十个居民时，陌生邻居晚上在家也会被当作同处一地，触发「偶遇、打招呼」。
* **场所容量只到整个场所。** 咖啡馆满没满只看总人数，不看大家要用的是座位区还是柜台。

`city_map.py` 早就会解析 citymap 里 `- Floor: / - Flat:` 的楼层与户（`city_map["interiors"]`），但没有任何地方用它。

## 2. 做了什么

### 2.1 后端空间树

`gaworld/world/spatial_tree.py` 把前端的 18 种布局（住宅、公寓、旅馆、医院、诊所、药店、学校、图书馆、商店、咖啡馆、
餐厅、办公、政务、工厂、车站、健身房、公园、公共空间）原样搬到后端，连同存储 / 索引接口（`find`、`locate`、`by_slot`、
`resolve`、`arena_for_activity`…）。选布局的规则也照搬前端的 `layoutFor`（见 `docs/superpowers/specs/2026-10-04-indoor-location-layouts-design.md`）：
先看 `interior_type`，再看 `amenity / shop / office / tourism / leisure` 等用途标签，再看建筑类型，再看名字，最后看地图 `category`，
都不认识就是公共空间。前端按地点做的镜像只是显示，房间不变。
活动 → 家具槽位（睡觉 → `sleep`，做饭 → `cook`，健身 → `exercise`…）用 `site/dashboard/indoor-view.js` 那一版规则。

**前后端不会走样**：`tests/test_rooms.py` 用 node 加载两个 JS 文件，逐个房间、逐件家具比对布局，在一组样例地点上比对选中的布局，
在一组样例活动上比对槽位。前端以后再改布局，这几项测试会先失败。
后端只多三项前端没有的数据：`default`（无事可做时待的房间）、`staff`（在这里上班的人的房间）、`staff_only`（访客不进的房间）。

### 2.2 打开 `local_physical.rooms` 之后

1. **分户。** 住宅和公寓布局的楼里，每个家庭（family 插件的 `household_id`；没有就是自己一个人）分到自己的一户。
   户来自 citymap 的 `Floor / Flat`；户数不够就往上加层（每层户数同顶层，没写户的楼每层 4 户，按 `3A / 3B` 命名）。
   分配是确定的（按家庭 id 排序、用 id 的散列挑空户），中途搬进来的家庭只占新户，不打乱已有分配。
2. **每步放进一个房间。** 移动阶段之后（新钩子 `agent.moved`）按正在做的事选房间：
   有对应家具的房间优先，其次别名（睡 ↔ 病床、点单 → 座位、看电视 → 椅子…），其次同类型的房间；
   都没有时，在这里上班的人去员工房间，其他人去默认房间（咖啡馆的就餐区、诊所的等候区、工厂的办公室…）。
   访客进不了员工房间（咖啡馆和餐厅的厨房、商店和药店的库房、学校办公室、政务办公室和档案、工厂车间和仓储、办公楼的开放办公区）。居民在家、家居插件已经告诉他在哪个房间时，就用那间——他被告知的房间就是他所在的房间。
   房间仍然合适就不换；同一户里同一时刻床和椅子不共用（第二个睡觉的人去第二间卧室）。在路上没有房间。
3. **同屋才算碰面。** `detect_co_located_agents` 在同一地点之外还要求同一户、同一房间。任何一方没有当前地点的房间
   （没开、刚到还没放）时退回只看地点，所以关着时行为完全不变。
4. **场所容量按房间算**（`local_physical.capacity` 也开着时）。房间容量 = 场所容量 × 该房间占布局面积的比例
   （布局里的房间铺满单位正方形，比例加起来是 1）。一个活动能用的房间都满了，这个场所对他才算满，
   然后照旧改去附近同类、开着门、有空房间的地方，或被拒；拒绝理由写明是哪个房间满了（「【咖啡馆】的就餐区已经满了…」）。
   放行时记下房间（`locations.room_intent`），路上的人按那间计数，到了就坐那间。
5. **进轨迹。** 每步的轨迹记录 `room: {node, unit, arena, object}`。室内渲染器（像素小镇、控制台与回放共用）按它摆人，
   住宅楼一次显示一户（选中居民所在的户，否则人最多的那户），标题写出户号和本楼有几户有人。旧轨迹照旧按活动猜。

## 3. 设计取舍（引用前必读）

* **布局按地点用途共用。** 每家咖啡馆都是同一套房间；房间是布局的，不是这座城市真实建筑的。
* **只有住宅、公寓布局分户。** 家在别的布局里（比如名字和类别都认不出、落到公共空间的节点）的居民，在家时与同楼的人共用房间。
* **按面积分容量是 (c) 级的约定。** 咖啡馆的就餐区占 45%：容量 10、一个居民代表 1 人时，只坐得下 4 个吃饭的人。
  所以开了房间之后，同一场所对**单一活动**的有效容量比只按场所算时小——更早满。关于「被拒多少」的结论要在开关两种设定下都看。
* **不进感知。** 居民不会被告知自己在场所的哪个房间（在家时家居插件那一行照旧）；房间只决定碰见谁、容量怎么算。
* **住宅楼里的访客不进任何一户。** 不住这栋楼的人待在楼里的公共区域，只会碰到别的访客。
* **同一时刻的先后。** 先处理的人看到的是后处理者上一步的房间——与地点本身的更新方式一致。
* **默认关。** 开了会改变谁碰见谁（以及开容量时谁进得去），前后 run 不可比；默认运行不变，不需要新的可比性版本。
* 按天快进、群体模式不逐步移动，不分房间。

CONFIG["local_physical"]["rooms"] = {"enabled": True}
