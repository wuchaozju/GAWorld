# 组织智能重设计：从组织理论到对照实验，再到合作任务

日期：2026-10-26。状态：用户已确认，六步流程已实施；验证记录见 `docs/reports/2026-10-26-organization-intelligence-redesign-verification.md`。本次受控验收不代表已完成真实模型研究。

## 1. 产品目标

用户上传一篇组织研究论文，或描述一种组织方式，系统把它转为可执行的协作规则，与选定的基本组织方式在同一类问题上比较。实验结束后，系统报告新组织方式在什么条件下更有效、效果有多大、代价是什么。用户可以把该组织方式保存到“合作任务”，供后续 AI 协作选择。

主流程：**提供组织材料 → 选择对照方式 → 选择问题 → 对比实验 → 结果报告 → 用于合作任务**。

主标题建议：“哪种组织方式，更适合解决这类问题？”

“人换了，组织还会吗？”成为可保留的专题实验，历史 OI-1、OI-2 记录按原协议查看，不迁移为新实验结果。新流程使用独立的协议版本。

## 2. 现有实现与方案选择

本次已核对当前工作区：

- `gaworld/research/organization_intelligence/protocol.py` 的 OI-1 固定训练、换人、保留档案等条件；`v2/protocol.py` 的 OI-2 只接受题目种子与重复组数，使用固定规则且不调用模型。二者不能直接承担任意组织规则与 benchmark 的比较。
- `gaworld/research/workbench.py` 和 `gaworld/apps/research_api.py` 已有论文解读、PDF/TXT/Markdown 提取，可复用读取能力；组织规则提取需要新增结构化输出和来源对应关系。扫描 PDF 当前没有文字提取能力，首版提示粘贴可读文本。
- `gaworld/collaboration/cooperation.py` 已有任务规划、成员执行、同伴审阅和负责人汇总；`models.py`、`service.py` 和前端请求尚无组织方式版本字段，需要新增策略执行入口。
- 合作任务已有内核插件；新能力接入现有插件、服务和页面。新 API 使用 delegate 路由及 OpenAPI，不继续扩大 dashboard handler 分支。
- 当前工作区含多处既有修改。实施必须基于现状增量修改，保留无关改动和已有研究记录。

三个可选路径：

| 路径 | 取舍 |
| --- | --- |
| **共享组织规则与执行器，先做完整六步流程（推荐）** | 需要扩展合作任务执行能力，但实验过的组织方式可以直接用于实际任务，后续新增 benchmark 也可复用。 |
| 只重做实验页，运行时用文字提示模拟组织 | 初期改动较少；通信限制难以真正执行，实验与实际合作容易变成两种实现。 |
| 先建完整组织建模平台和任意代码 benchmark 插件市场 | 扩展面大，但明显超出当前六步流程；首版投入和验证成本高。 |

推荐第一条。先完成一个可跑通、可导入 benchmark、可保存组织方式的完整流程，再扩展规则类型。

## 3. 六步用户流程

### 第一步：提供组织材料

入口为“上传论文”和“描述组织方式”，支持 PDF、TXT、Markdown 或直接粘贴文字。用户选择用于解读的模型，界面明确解读会调用模型。

按钮：“分析组织方式”。结果为可修改的“组织方式卡片”，包括：

- 组织名称、要解决的协调问题、预期优势及可能失效的条件。
- 成员如何分工、信息如何分配、谁能与谁沟通、先后顺序、谁来决定最终答案。
- 如何审阅、发生分歧如何处理、是否保留共享经验、何时停止。
- 每条规则对应的原文段落或页码；没有页码时用文本片段定位。
- 区分“材料明确描述”“系统为运行补充”“用户修改”。保留修改记录。

论文中的理论描述不能自动视为完整的执行规则。关键规则缺失时给出明确建议供修改；无法表达的机制列为“本次暂不能实现”，阻止把不支持的方案直接标为可运行。不得把未支持的机制悄悄改成普通群聊。

按钮：“采用这份组织方式”。后续可以返回编辑，但修改后需重新保存实验设置。

### 第二步：选择对照方式

首版提供四种基线，并让用户看到同样格式的组织方式卡片：

| 基线 | 固定规则 |
| --- | --- |
| 随机网络（默认） | 默认无向、无自环、连边概率 0.5，不强制连通。按种子为每个题目/重复实例生成通信边，题内固定，每轮仅沿允许边传消息。参数、实际边、轮数与最终汇总规则均写入设置。 |
| 全员互联 | 所有人可见上一轮所有成员的消息，同轮看不到尚未提交的消息。 |
| 层级组织 | 成员向指定负责人报告，负责人分派或反馈并汇总；不自动开放成员间横向通信。 |
| 独立作答后汇总 | 成员独立完成，过程中不通信；客观答案按事先固定的投票规则汇总，开放成果使用指定汇总步骤。 |

默认采用“仅比较通信结构”：双方使用相同的决策/汇总规则、记忆规则与资源上限，只改变通信边。若候选方案还改变分工、审阅或记忆，界面自动标为“比较整套组织方式”，报告只能评价规则组合的效果。

共同的默认终稿规则：选择题对成员最终提案等权投票，平票按选项 ID 排序；其他任务由固定的第一个角色槽位在只读终稿阶段汇总成员提交的成果，不再发起追问，调用计入任务预算。这个共同读出步骤单列在组织卡片中，不把最终读取所有终稿误画成讨论期间全员互联。候选方案要求另一种决策规则时，切换为整套组织方式比较。

随机网络的抽样属于实验重复的一部分。固定种子不能消除某一张图的偶然优势，因此需要跨网络实例重复，记录每个实例的实际边与拓扑参数。一个 seed 不能保证外部模型输出完全可复现。

### 第三步：选择问题

用户先选择“要解决哪类问题”，再选择内置题库或导入 benchmark。首版内置两类可客观评分的任务：信息分散的选择题、带约束的资源分配题。

首版 benchmark 导入支持 JSONL、CSV，使用字段映射和预览完成验证。每题至少包含题目 ID、类别、题干；按评分类型补充选项、参考答案或约束/目标。存在局部信息时必须声明按成员槽位分配的观测，否则默认所有成员得到相同题干。

上传的数据包包含题目；另行选择系统注册的评分器。数据包不包含可执行代码。对新评分逻辑，通过受信任的 Python 适配器注册，不执行上传的脚本。

适配器职责：读取题目、构造成员可见输入、解析最终答案、评分、声明评分方向和范围、给出版本和内容哈希。参考答案与评分器隐藏数据只能交给评分端，不能出现在成员或汇总者上下文中。

支持的评分模式：

- 客观题：准确率、正确答案匹配。
- 约束/优化题：约束满足率、事先确定的目标值或相对最优得分。
- 开放题：固定量表与评审模型、隐藏组织名称、平衡呈现顺序，结果明确显示“模型评审”。未配置评分依据时只能试运行并查看成果，不能生成效能优劣结论。

导入完成时显示题数、类别、重复 ID、缺失字段、评分器兼容性和预览。题库版本、抽样规则、练习/正式测试划分和抽取的题目在启动前固定。

首版正式比较逐题重置记忆。若材料要求持续学习或成员更替，标记为需专门实验协议；不把不能测试的机制纳入首版结论。后续可把历史换人实验实现为独立适配器，保留训练/测试隔离。

### 第四步：形成两种组织并运行

用户看到左右两张组织方式卡片、通信图与流程说明，以及共享的实验设置：题目、参与成员、模型、重复次数、资源上限、评分方式。

默认从当前世界选取同一批居民，建立两份隔离的成员状态快照。双方的成员身份、能力、初始记忆和题目局部信息分配相同；组织方式只决定之后如何分工、通信、审阅和决策。若需要比较不同角色配置，必须明确作为整套组织方式比较的一部分。

“更多设置”包含轮数、模型参数、重试上限、超时、随机种子、主指标、实际有意义的最小差异和预算。日常设置用普通中文，技术指纹放在详情中。

保留两个独立按钮：

1. **保存实验设置**：固定组织版本、模型与评分器设置、题目和成员快照、种子、样本量及分析规则，显示预计调用量与可获得的费用估算。
2. **开始实验**：用户主动启动实际模型调用。预检模型、额度、规则支持和题库完整性，失败时展示具体原因。

公平性由执行器保证：

- 相同模型及参数、成员数量、输入信息总量、每成员上下文上限、总输入/输出 token 和通信轮次上限。仅用相同调用次数不足以说明相同计算成本。缺少可靠 token 计量时，改用预先声明的调用、上下文长度和输出上限，报告称为相同运行限制，不声称相同 token 消耗或成本。
- 组织内部的规划、通信、审阅、修订与汇总全部计入任务预算；材料解读和最终报告调用单独计量。
- 双方使用相同资源上限，不强制耗尽；实际调用、token、耗时与完成率分别报告。provider 未返回 token 或价格时标为未知，不能用字符数冒充。
- 每个题目与重复组形成一对实验。角色槽位映射固定或预先随机化；双方运行顺序平衡，不把全部候选条件固定放在后面。
- 不允许读取另一组消息、历史任务答案或正式测试参考答案。消息可见性由代码过滤，不能仅靠 prompt 要求“不要看”。
- 实验内成员记忆和共享记录写入隔离目录，研究运行不写回真实居民记忆。

进度显示双方完成题数、当前成员与步骤、已用资源、错误及预计剩余任务。支持暂停、继续与终止；恢复时校验协议和执行器版本，不重跑已完成记录，不自动切换模型。

## 4. 第五步：分析与报告

先展示主指标的两组成绩、配对差异与不确定区间，再展示各问题子类、完成率、约束满足率、通信量、耗时及资源消耗。成绩和成本分别呈现，不在事后调权合成一个偏向候选方案的总分。

启动前固定一个主指标、方向、样本量和最小有意义差异 δ。支持完整测试集时使用全量，否则保存固定抽样。小样本试跑只验证流程与估计成本，不能因暂时领先自动结束正式比较。

默认试跑使用最多 5 道题、每题 1 次；正式比较使用最多 100 道独立题、每题 3 次。少于 30 道独立题时默认只给探索性差异，不启用“有证据更有效/更差”状态；30 是产品的最低报告门槛，不代表统计功效保证。正式运行前用独立试跑的差异波动提示精度不足，用户可增加题量。δ 默认 0，结果措辞为“成绩更高”；只有用户事先设定正的 δ 时，才称为“达到设定的实际改善幅度”。题库没有明确量纲、方向或失败分时不可启动正式比较。

以题目为统计簇：同一题的多次模型运行、消息和网络实例不是独立的新题。先计算题内配对差异，再跨题汇总；95% 区间用预先固定的题目簇 bootstrap。若以后加入跨题学习，改用独立组织运行作为统计单位，不能继续套用逐题独立分析。

统一把差异方向变换为“正值代表候选组织更好”。结论规则：

| 状态 | 判定与措辞 |
| --- | --- |
| 有证据更有效 | 达到正式比较报告门槛、数据完整且主指标差异的 95% 区间下界大于 δ；同时列出成本及适用范围。 |
| 有证据更差 | 达到正式比较报告门槛、数据完整且差异区间上界小于 −δ。 |
| 尚无充分证据表明更有效 | 其他完整结果，包括区间跨零、差异未达到 δ 或样本不足以分辨差异；不能写成“两种方式一样”。 |
| 暂不能判断 | 运行未完成、评分缺失、协议不一致或预算规则被破坏。 |

“在成绩上更有效”不自动意味着更省资源；若成绩提高但实际资源使用更高，报告必须并列说明。跨多个 benchmark 的比较分别出结果；整体优越性的主张需要预先声明聚合/校正规则。首版的子类分析标为探索性，不用挑出的最好子类替代主结果。

失败处理在启动前固定：正常任务过程中的超时、无效答案、约束违反计入完成率，并按题库预先声明的失败分计入主指标；基础设施中断保留记录并恢复，不补零或删除失败行来制造优势。恢复后仍缺正式实验单元则保持“暂不能判断”。重试消耗计入原单元预算。

报告包含材料与规则来源、系统补充假设、两组实际规则、题库与样本范围、模型/预算、运行完整性、主结果、成本、失败案例和结论限制。每项数值结论链接到统计表和题目记录。模型可以解释结果与生成可读报告，但优劣状态由代码根据固定规则产生，报告生成失败不能丢失统计结果。

提供 Markdown 报告、JSON 实验设置、CSV 逐题成绩及可下载的运行记录。报告结论模板：

> 在本次选定的模型、成员、题库和资源上限下，候选组织在主指标上【有证据更有效／有证据更差／尚无充分证据表明更有效】。观察到的差异为……，95% 区间为……，实际资源消耗为……。结论适用于本次测试范围。

## 5. 第六步：保存并用于合作任务

按钮：“保存到合作任务”。用户填写名称、简介、适用问题和推荐人数，系统保存实验中实际使用的组织规则版本，并附上来源研究和结果状态。

保存的是可执行规则，默认不包含 benchmark 题目、参考答案、成员私有记忆或这次实验聊天记录。没有证明优势但已验证可执行的组织方式仍允许保存，显示“尚无优势证据”或“本次表现较差”；保存动作不等于认证。

“合作任务”新增“组织方式”选择器：保留现有默认方式，并列出当前用户在当前世界保存的方式。卡片显示做事流程、适用人数、证据范围和版本。选择后实际改变消息传递、分工、审阅、决策和停止条件。

组织规则引用角色槽位而非实验中的居民 ID；开始合作任务时把选定居民映射到槽位。人数不符或规则能力不受支持时，在开始前说明原因，不自动换成另一种组织方式。用户可调整人数或另存新版本。

合作会话保存完整组织规则快照和版本。后续修改组织方式生成新版本，已经开始的任务不受影响；未来任务可选择新版。换用其他模型、题型或人数时显示“超出已有实验范围”，仍允许作为未验证配置使用，不沿用原来的优势结论。

## 6. 共享技术结构与接口边界

三个核心对象：

- **组织方式版本**：来源材料、来源片段、规则及来源类别、角色槽位、通信/分工/审阅/决策/记忆/停止规则、人数限制、支持状态、版本与内容哈希。
- **Benchmark 版本**：题目、成员可见输入与隐藏评分数据的边界、类别、评分器及版本、方向/量纲、划分、内容哈希。
- **对照研究**：两种组织版本、成员快照、题库快照、资源上限、模型配置、题目/重复配对、统计与失败策略、调用记录、结果及报告。

在 `gaworld/collaboration/` 下新增组织规则模型、验证器、版本存储与共享执行器。执行器负责步骤调度、收件人约束、上下文构造、预算和最终产物；注册表只允许受支持的规则原语。现有 `CooperationRunner` 保留为默认兼容路径，新策略走明确的执行入口。

首版规则原语限定为：固定角色槽位与任务分派、私有工作、按图交换上一轮消息、指定成员审阅、有限次数修订、投票或指定成员汇总、固定轮次/预算停止。候选方式可以组合这些原语；规则生成由模型建议，规则验证与执行由代码完成。材料要求原语外能力时，必须显示具体缺项。

在 `gaworld/research/organization_intelligence/` 下新增独立的 comparison 子包，负责材料到规则、benchmark 适配、实验设置、配对运行、分析与报告。研究与实际合作调用同一执行器，区别在于输入适配、状态隔离与评分记录。组织方式是否一致由规则哈希和执行器版本校验。

建议新 API 使用独立前缀 `/api/research/organization-intelligence/comparisons`，保留旧研究接口；组织方式列表与版本读取由 `/api/collaboration/organization-methods` 提供。合作会话创建接口新增可选组织方式 ID 与版本，服务端验证权限并保存快照，不信任前端自带的结论或规则。

新 API 同步增加 delegate 路由、OpenAPI、账号策略与额度记录。研究、组织库、benchmark、报告和任务产物全部带用户与世界归属，后台任务携带同样上下文。路径按请求的 `world_paths.effective_config()` 解析；合作服务缓存按用户/世界及相关配置隔离，不能复用绑定其他世界居民的全局实例。

组织规则用于执行协作任务，与城市内组织治理实体保持各自职责。此功能复用已有协作插件，不在 `generative_city_sim.py` 增加逻辑。

## 7. 页面结构

仍从现有 `/console` 研究工作台进入“组织智能”，沿用主题、世界选择、权限和返回路径。页面保持一份主标题，六步导航展示已完成和待完成状态；返回上一步不会丢失材料。

前期主区域为当前步骤，侧栏显示“待比较的两种组织”和预计任务量。开始后进入运行视图；结束后默认打开结果视图，并提供“查看组织规则”“查看每道题”“下载报告”“保存到合作任务”。历史实验与专题模板放在单独入口，不能盖过新的主流程。

首版包含中文与英文文案、深浅主题、手机宽度布局、状态提示与键盘可操作性。技术 ID、哈希和原始 JSON 进入可展开详情。

## 8. 实施顺序与验收

按依赖推进，共用本设计，不把终点缩成只改界面：

1. 实现组织规则版本与共享执行器，四种基线可真实执行；验证通信隔离、预算、默认合作兼容。
2. 实现材料提取与审阅、内置题库和 JSONL/CSV 导入、评分边界及实验保存。
3. 完成两组配对运行、暂停/恢复、确定性统计与报告导出。
4. 完成六步页面、组织方式保存、合作任务选择与实际调用，联通用户/世界权限。

首版验收场景：

- 上传一份可读论文和一份自由描述，均得到可编辑且可追溯的组织规则；不支持机制有具体提示。
- 选随机网络和内置题库，保存设置后没有实验调用；点击开始才启动双方真实模型任务。
- 导入自定义 benchmark，预览字段与评分；成员/汇总者上下文均无参考答案或另一组记录。
- 固定模拟模型输出后，能够精确验证收件人、轮次、汇总、预算与评分；真实模型小规模试跑另行验证，不把 mock 结果当作科学证据。
- 暂停/恢复不重复完成单元；中断、无效答案、缺数据、优势不足和明显负结果均有正确状态。
- 在可手算的配对结果上核对差异、区间方向、δ 和结论；同题重复不会虚增独立题数。
- 保存组织方式后，在“合作任务”选中并完成一次任务；日志证实实际使用相同规则哈希与执行器版本。
- 检查匿名/登录、越权读取、跨用户/跨世界、后台世界切换、深浅主题及手机流程；文件导出同样检查权限。
- 修改组织方式产生新版，旧实验与旧会话可按原版查看；旧 OI-1/OI-2 记录保持可读。

实施时遵循仓库测试要求，覆盖新代码，运行相关研究/合作/API/OpenAPI 测试、核心套件和 lint ratchet。浏览器端验收过程、程序证据和未执行的真实模型研究须分别记录，不把功能完成解释为科学结论成立。
