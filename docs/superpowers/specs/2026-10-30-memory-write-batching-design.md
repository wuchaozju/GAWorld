# 记录阶段的记忆写入合批

用户要求继续已确认的工程加速方案。本轮选择同一记录阶段内的四次 SQLite 提交合并；轨迹格式迁移和跨阶段缓冲的兼容范围更广，另行处理。

## 边界

`_stage_record` 连续写入 log、plan、reflection、action，中间没有认知读取。合批仍按原顺序净化文本、生成嵌入和时间戳，所有 payload 准备好后在一个事务内写入，在下一阶段/下一居民开始前提交。模型与嵌入调用数量、顺序、内容及正常运行的存储结果不变。

episode 写入后紧接记忆回顾，必须保持原即时提交；不把它和 record 合并，不跨 tick 缓冲，不更改日志/Recorder 的刷新或轨迹输出格式。

该存储 API 与原单条 API 一样会在退出时提交连接，不支持嵌套在调用方自管事务中；“嵌入在写事务外”的保证以入口尚未开启事务为前提。正常 record 调用满足该前提。

保留单条 `vector_db_add_entry` API，将相同净化、嵌入及权重实现统一到小批量 `vector_db_add_entries`。空文本不生成嵌入，空批次不创建数据库。嵌入计算在写事务外，避免持锁等待网络嵌入。成功返回即对其他连接可见；批内数据库错误整批回滚，不留下半套记录。该失败语义明确优于原四次独立写入，但不声称异常时仍保留相同的部分结果。

使用已有计时器记录 `memory.write`（一次单条或合批调用）；阶段计时仍是包含内部写入的累计耗时。

## 验收

先以旧 record 路径验证四次 COMMIT 的失败断言。真实临时 SQLite 测试覆盖结果与单条路径一致、顺序/权重/时间戳、一次事务、空批次、嵌入错误、SQL 错误回滚、外部读可见性、线程写入，以及实际 record 集成。执行记忆/回顾/认知/核心回归和 lint，独立审查。以临时 WAL/NORMAL 数据库测原四次提交与新单次提交，验证记录及查询结果一致，再报告局部耗时；不能扩展为真实模型整场提速。
